0這份手冊的範圍

本手冊寫的是把 ANILA v1.0.1 出貨包裝上內網平台主機、驗證、之後維運的完整流程。它假設：

  • 平台主機在氣隙內網，沒有網際網路；所有東西用出貨包帶進去。
  • 登入方式是自然人憑證卡（card-only），同仁沒有帳號密碼。
  • 模型在另一台模型主機（aiagent2 gateway），平台透過 https 呼叫；平台主機本身不跑模型。
  • 操作者會用 Linux 終端機與 Docker，但不需要懂平台內部。

需要更深的細節（每一步的手動備援、歷史教訓）時，看第 14 節列的 runbook；本手冊是主線，runbook 是附錄。

版本規則：這條線從 2026-09-02 起以 v1.0.0 重新起算，之後修 bug 升 patch（v1.0.1）、加功能升 minor（v1.1.0）。舊線（2026-07 以前）的 v1.x／v2.x 全部是 legacy，號碼比較大不代表比較新，不要拿舊線的東西回來用。

2出貨包裡有什麼

出貨包是 anila-YYYY.MM.DD-N.tar.gz（約 4 GB），由開發機 scripts/release/build-release.sh 從乾淨的 git HEAD建出來；版本是台北日期。解開後是一個目錄：

anila-YYYY.MM.DD-N/
├── anila-update.sh    ← 安裝／更新／回復／認領
├── preflight.sh        ← 主機預檢，不改任何東西
├── manifest.txt        ← 版本、commit、每個檔案的 SHA256
├── manifest.sha256
├── images.tsv          ← 映像清單與來源 digest（含 redis）
├── source.tar.gz       ← 這一版 HEAD 的原始碼
├── compose/
│   ├── compose.yaml
│   └── platform.yml
└── images/             ← 每個映像一份 docker save 封存

包裡沒有 .env、secrets/、憑證私鑰、備份。密鑰、憑證、JWT 都在內網主機上由 anila-update.sh 產生，放進 /opt/anila/state/，不進版本目錄。

打包時做三道檢查：① 工作目錄必須乾淨（不能用未提交的檔案建映像）；② 每個封存逐層掃描不得夾帶私鑰（含 redis 層，BEGIN … PRIVATE KEY 也算），已知的公開測試憑證例外；③ 產出後逐檔核對清單與 SHA256。任何一道紅就停。

3帶進內網的清單

要帶從哪來用在哪
出貨包資料夾（整個）開發機 build-and-export第 5 節載入
對應版本的 repo（程式碼與文件）同一個 tag 的 checkout 或壓縮檔compose 檔、nginx 設定、安裝腳本、本手冊都在裡面
server.pfx（平台網域的 wildcard 憑證＋私鑰）IT／憑證管理單位nginx 的 https

5安裝：出貨包的 anila-update.sh

出貨包解開後，跑包裡的 anila-update.sh（第一次安裝與更新同一支）：

sudo tar -xzf ~/anila-YYYY.MM.DD-N.tar.gz -C /opt/anila
sudo bash /opt/anila/anila-YYYY.MM.DD-N/anila-update.sh /opt/anila/anila-YYYY.MM.DD-N

先跑預檢，每一條 ✗ 都附要執行的指令，全綠再安裝：

sudo bash /opt/anila/anila-YYYY.MM.DD-N/preflight.sh ~/anila-YYYY.MM.DD-N.tar.gz

腳本做這些事（順序固定，失敗自動回復）：

步做什麼你要做的
取鎖與核對清單安裝根目錄取排他鎖、逐檔核對出貨清單與 SHA256—
備份（更新時）停寫入服務、備份資料庫與檔案快照，記下備份時間與當時的 alembic 版本—
解壓與載入映像解到 /opt/anila 底下、docker load 後用清單的映像 ID 核對看它全綠
準備目錄與密鑰產 state/.env（5 把密鑰：SECRET_KEY、ADMIN_PASSWORD、CSP_DB_PASSWORD、CSP_APP_DB_PASSWORD、CODESERVER_PASSWORD，寫在 state/generated-secrets.txt）、JWT 金鑰、模型 CA、檔案所有權把密鑰檔案抄進密碼管理器
啟動與健康檢查先不起 nginx，內部健康檢查（含 CSP /health）過了才開入口看第 6 節

腳本會問的問題

問題不是固定序列：它依主機上已經有什麼決定要不要問。不要把一串固定答案 pipe 給它。

問題什麼時候出現怎麼答
image 包資料夾路徑沒把路徑當參數出貨包絕對路徑

無人值守

6首次啟動後的驗證

6.1 容器

docker compose -p anila ps
# 期望：csp / csp-db / redis / nginx / router / anila-ui / ingestion-worker /
#       anila-studio / pptx-renderer / asr-gateway 全部 healthy 或 running
#       （解碼端不在這台，不會有 asr-decoder 容器）

6.2 五個入口（看 Content-Type，不要只看 200）

H=https://anila.ai.ncsist.org.tw
curl -sk -o /dev/null -w '%{http_code} %{content_type}\n' $H/            # 200 text/html   治理中心
curl -sk -o /dev/null -w '%{http_code} %{content_type}\n' $H/anila/      # 200 text/html   對話介面
curl -sk $H/health                                                        # {"status":"healthy",...}
curl -sk -o /dev/null -w '%{http_code}\n' $H/anilalm/                    # 503  刻意關閉，正常
curl -sk $H/.well-known/jwks.json | head -c 80                            # 要有 "keys"，回 500 = JWT 金鑰沒產

6.3 治理中心

用擁有者的卡刷進治理中心（網址根目錄）。不應有任何憑證警告；有＝憑證沒換到 wildcard 或 DNS 沒生效。

在內網主機上，模型的健康燈應該是綠的；不是綠的先查 MODEL_GATEWAY_API_KEY、模型主機 DNS 與 share/pki/model-ca.pem，不是平台本身。（開發機上這一格必然紅，因為連不到模型主機。）

7初裝六件（腳本不會替你做的）

前五件的共同點：漏掉不會有錯誤訊息，症狀出現在同仁開始用的那一刻。第六件會報錯，但錯在第一個問題。

7.1 建立單位

擁有者刷卡進治理中心 → 部門 → 新增。擁有者進場不需要單位存在，所以這個順序才通。

7.2 擁有者密碼（破窗用）

.env 的 ADMIN_PASSWORD 只在擁有者帳號被建立的那一次被消費。帳號建好之後再改 .env，資料庫裡的密碼不會變，而且沒有任何錯誤訊息。要換密碼用治理中心 → 使用者 → 重設密碼。首次安裝時 .env 裡的值就是能登入的密碼，請存進密碼管理器。

7.3 JWT 簽章金鑰

anila-update.sh 的「準備目錄」那一步已產。漏掉的症狀是「起來了但登入炸」：/.well-known/jwks.json 回 500，登入發不出權杖，anila-studio 反覆重啟。金鑰在 /opt/anila/state/secrets/；補完重建 csp 並重載 nginx：

cd /opt/anila
sudo docker compose -f current/compose.yaml -f current/.anila-images.yml -p anila up -d --no-build --pull never csp
sudo docker exec anila-nginx nginx -s reload

7.4 CSPKI 憑證清單

檔案來源去處驗證
server.pfxITinfra/nginx/certs/server.{crt,key}openssl x509 -in server.crt -noout -subject -dates → CN 是 *.ai.ncsist.org.tw
CSPKI CA bundlerepo 內建share/pki/model-ca.pemecho | openssl s_client -connect <模型主機>:443 -CAfile share/pki/model-ca.pem 2>/dev/null | grep 'verify return code' → 0 (ok)
secrets/dev-card-ca/開發機不進內網內網主機上不該有這個目錄

ANILA_MODEL_CA_FILE 是「取代」整個信任庫，不是疊加：指到空檔或壞檔，csp 所有出向 https 全掛。先在主機上驗到 verify return code: 0 再交給容器。

7.5 指定主路由模型

治理中心 → 模型 →「註冊模型」，登錄模型主機的端點；再到同頁「模型角色」指定七個角色（主路由模型、平台嵌入模型、簡報模型、生圖模型、視覺模型、摘要模型、知識庫對話模型）。沒有主路由時，同仁問第一個問題就回「ANILA Router 無可用主路由模型」。

7.6 規章知識庫標成「ANILA 可檢索」

治理中心 → 知識庫 → 該知識庫的開關。新建的知識庫預設沒有標；沒標的話規章問答整個不存在，畫面看起來正常，模型憑印象編條號。

8端到端驗收

六件做完，用一張真的卡（不是擁有者）走一遍，每格留下產物（截圖或回應碼），不要只打勾：

#做什麼判準
1同仁刷卡 → 註冊選單位 → 等待核准治理中心 → 使用者「待審核」變 1
2管理員核准 → 同仁再刷卡進到 /anila/，左下顯示他的名字
3問一題規章問題答案上方有步驟清單，下方有「查看 N 筆來源」，來源側欄有檔名
4問一題非規章問題答案上方寫「本次未檢索院內規章」
5上傳一份 PDF 到知識庫狀態變 indexed；問它的內容答得出來
6治理中心 → 用量剛才的請求有記到
7破窗（第 12 節）/login?show_alternatives=1 出現帳密欄位，擁有者真的登得進去；記下登入後右上的角色
8拔卡、關瀏覽器、重開要重新刷卡才能進

第 3、4 項在同一個對話裡問，最能看出平台「查了」和「沒查」的差別。

9更新到新版本

每次更新都是一個新的出貨包（版本是台北日期 YYYY.MM.DD-N）。更新會自動先停寫入、備份資料庫與檔案，失敗自動回復；.env、secrets/、憑證、share/ 都在 state/，不會被蓋掉：

sudo tar -xzf ~/anila-YYYY.MM.DD-N.tar.gz -C /opt/anila
sudo bash /opt/anila/anila-YYYY.MM.DD-N/preflight.sh ~/anila-YYYY.MM.DD-N.tar.gz
sudo bash /opt/anila/anila-YYYY.MM.DD-N/anila-update.sh /opt/anila/anila-YYYY.MM.DD-N

退回上一版是 sudo bash /opt/anila/anila-update.sh rollback（會先列出會消失的對話／訊息／文件筆數，打字確認才還原）。這台早有同名的 compose 專案卻沒有安裝記錄時，先用 ... adopt /opt/anila/versions/<目前版本> 認領。完整判準見 docs/deploy/UPDATE.md；更新後照第 6 節再驗一次。

更新後請同仁硬重新整理（Ctrl+Shift+R）。 還開著的舊分頁點下一頁時會去抓已經不存在的舊檔案，症狀是點了沒反應或畫面空白。發一則公告最省事（治理中心 → 公告橫幅）。

手動只重建單一服務時也要重載 nginx。 例如 up -d csp 之後全站 502、但 docker compose ps 每個都綠，就是這個。

改了 infra/nginx/anila.conf 要 up -d --force-recreate nginx，不是 restart：那個檔是單檔掛載，編輯器換了 inode 之後容器仍抓舊檔，沒有任何錯誤。

10日常維運

10.1 備份與還原

每天的備份由 compose 的 backup 服務做，不是 crontab，也不用再跑 backup-csp-db.sh：容器起來先備份一輪，之後每 24 小時一輪，寫到 state/share/backups/，保留 14 份每日、6 份每月。最後一次成功的時間顯示在治理中心儀表板；超過 36 小時或最近一輪失敗會發警報。

還原始於丟棄用的 Postgres 演練，核對列數，再談切回；還原前要先建 csp_app 角色，否則權限設定會靜默失敗。完整手順：docs/runbooks/csp-db-backup-restore.md。

10.2 憑證輪替

wildcard 憑證到期換發後，用院內新憑證覆蓋 /opt/anila/state/certs/server.crt 與 server.key，重建入口（... up -d --force-recreate nginx）。自簽的臨時憑證只在沒有正式憑證時才簽。CSPKI CA 換代時更新 state/share/pki/model-ca.pem 並重建 csp。憑證是目錄掛載，重建就讀得到。

10.3 停棧與起棧

# 全停（asr-gateway 也一起停；解碼端不在這台，沒有要帶的 profile）
cd /opt/anila
sudo docker compose -f current/compose.yaml -p anila down
# 全起
sudo docker compose -f current/compose.yaml -p anila up -d --no-build --pull never
sudo docker exec anila-nginx nginx -s reload

down -v 會刪掉資料庫。日常永遠不要帶 -v。

10.4 模型金鑰輪替、加擁有者

  • 金鑰：模型主機重簽 → 改 .env 的 MODEL_GATEWAY_API_KEY → up -d csp → reload nginx。
  • 加擁有者：治理中心 → 使用者 → 編輯角色（既有帳號）；或改 CARD_INITIAL_OWNERS（只對之後第一次刷卡的人生效）。

10.5 追蹤匯出與 Router 狀態

  • Router 的步驟追蹤匯出（ANILA_TRACE_ENDPOINT）出貨預設是關的，而且 csp 目前沒有接收端；使用者看到的步驟時間軸走的是即時事件，跟這個無關。不要設這個變數。
  • Router 多輪派工的中途狀態放在 named volume router-sessions（v1.0.2 起）；down 不會刪它，down -v 會。

10.6 附屬入口

nginx 對 /codeserver、/n8n 若回 404，/anilalm/ 回「暫時維護中」（503），那是刻意的發行閘，不是故障，不要為它們動 nginx。沒有 /gitlab/。要開放 ANILA LM 時照 docs/runbooks/anilalm-release-gate.md。

11語音輸入：gateway 在本機，解碼端在遠端

瀏覽器的麥克風按鈕只會打平台主機的 /asr/，nginx 轉給本機的 asr-gateway。解碼（語音轉文字）不在平台這包裡：解碼端是遠端的一台服務，位址與協定填在治理中心「外部服務」；gateway 一定要在平台主機上跑。

情況做什麼備註
有解碼端治理中心「外部服務」填語音那一筆（位址、協定、憑證）；位址若是私網 IP 或單一名稱，先加進「信任主機」gateway 隨平台啟動，docker ps 應看得到 anila-asr-gateway-1
沒有解碼端不必設定麥克風不出現
換解碼端改治理中心那一筆gateway 在 ASR_DECODE_URL_TTL（預設 60 秒）內重讀，不用重啟
# 驗證 gateway 看到的解碼端
docker exec anila-asr-gateway-1 python3 -c \
  "import httpx,json;print(json.dumps(httpx.get('http://localhost:8200/asr/health').json(),ensure_ascii=False,indent=2))"
# reason: ok = 健康；decoder_unreachable = 連不到；decoder_unauthorized = 金鑰錯（不要去查網路）

協定填錯的症狀是「麥克風看起來正常，每句話都失敗」；解碼端被出向檢查擋下時麥克風不出現，gateway 日誌會有 blocked 的 reason。.env 裡若還留著舊的 ASR_DECODE_*，服務不會讀，刪掉即可。

12卡登壞掉時的後路（破窗）

card-only 模式關掉了帳密登入。如果讀卡元件或 CSPKI 出問題，所有人進不來，包括你。兩條路：

  1. 畫面上的破窗：https://<平台>/login?show_alternatives=1，用擁有者帳密登入。後端只放行擁有者，其他人填了照樣進不來。
  2. 暫時切成帳密模式（讀卡環境整個掛掉時）：.env 改 ANILA_AUTH_MODE=password → up -d csp → reload nginx → 處理完改回 card-only 再做一次。
