# Runbook — 從畫面改設定（治理中心「平台設定」）

> 對象：平台管理員（admin 以上）。單顆設定約 1 分鐘，需要重啟的那類再加一次重開。
> 背景：這一頁之前，csp 的每一顆環境變數都只能改 `.env` ＋ recreate（運維動作，
> 氣隙內要重新交付才改得動）。現在 **96 顆設定全部上頁且都可從畫面保存**——包含 57 顆
> 從來沒出現在 compose、只吃程式預設值的隱形變數；A 類另受 username=`admin` 閘門控管。
> ⚠ **這一頁讓 96 顆都可保存，但保存不等於目前行程已套用**：改完什麼時候生效，逐顆是硬規則，寫在頁面上。

## 在哪裡

治理中心 → 側邊欄 **「平台設定」**（路徑 `/platform-settings`）。**admin 限定**（讀寫同一道門）。

## 四個區，各自的承諾不一樣

頁面依「改完會發生什麼」分四區。**區的標題就是那一區的承諾**，不要跨區推論：

| 區 | 存檔之後 | 你要做的事 |
|---|---|---|
| **改完立刻生效** | 下一個請求就是新值（每次請求都重新查 DB，沒有快取） | 沒有了。存完就結束 |
| **改得動，但要重啟才生效** | 值進 DB，**下一次開機**才會蓋過 env | 讓 csp 重開一次（見下節） |
| **可保存，但先看每列提醒** | 值進 DB；下一次 CSP 開機會重新驗證並同步到 Settings／env，跨行程或 import-time consumer 仍依每列提醒 | 讓 CSP 重建一次；若提醒指向其他行程，再同步該行程的部署設定 |
| **祕密：只能輸入，不回顯** | 值進 DB；下一次 CSP 開機重新驗證後同步到該行程，A 類永不回顯，其他行程仍看各自通道 | 只有 username=`admin` 可寫；必要時依列提醒輪替對應部署設定 |

> ⚠ 開機同步遇到檔案消失、值域失效或設定表讀取失敗時，最上方警示會列出退回的 key；
> 來源不是 `db-boot` 時，不要把 DB 列誤當成已生效。

每一列都有 **「來源」欄**（DB／env／程式預設）——**值沒生效的時候先看這一欄**，
不要先去翻 compose。來源說 `env`，就表示 DB 那一層沒有東西在贏；來源說 `db-boot`，
就表示現在跑的是這次開機從 DB 載進來的值。

## 「要重啟才生效」的那一區：存完之後

1. 存檔。頁面會回一句
   **`已儲存，重啟後生效：docker compose up -d --force-recreate csp；重開後回頭看這一列，「現在生效」要變成你存的值`**，
   而且那一列會**同時**顯示「現在生效」與「待生效（重啟後）」兩個值——
   兩個值不一樣是正常的，那就是這一區的全部意思。
2. 讓 csp 重建一次（**就是這一道，不要先試別的**）：

   ```bash
   docker compose -p <專案名> up -d --force-recreate csp   # 本機重啟樹是 -p anila-restart
   ```

   ⚠ **裸的 `docker compose up -d csp` 對這種改動必定什麼也不做。** 從畫面改設定
   只寫了一列 DB，**compose 檔與容器的設定雜湊一個字都沒變**，於是 `up -d` 判定
   「已是最新」而不重建容器——開機覆蓋不會重跑、你存的值不會生效，
   **而且不會有任何錯誤訊息**。`--force-recreate` 是明著要它重建，不吃那個比對。

3. **回頭看那一列**（這一步不能省，畫面那句話的後半講的就是它）：
   重建之後「現在生效」必須變成你存的值，來源變成 `db-boot`。
   如果還是舊值，先確認第 2 步的 `-p <專案名>` 有沒有打對（打錯專案名會去建一組新的容器）。
   👉 另一種情況：**改 compose／`.env` 的時候一律 `up -d`，不要 `docker restart`**
   （那一種的設定雜湊會變，`up -d` 自己就會重建；原因見
   [`restart-vs-recreate.md`](./restart-vs-recreate.md)）。

4. 頁面最上面如果出現紅字 **「這次開機沒有載入設定覆蓋」**，
   代表這一次開機**一顆覆蓋都沒有套上去**，現在跑的是 env／compose 或程式預設。
   標著「重啟後生效」的承諾這一輪全部落空——banner 上會寫原因，先解決它再談設定。
   （這是刻意的 fail-soft：載入失敗時服務照樣以 env 值開機，但**絕不假裝覆蓋生效了**。）

## 「可保存，但先看每列提醒」的那一區：真的要生效的時候

**每一列的提醒就是那一列的操作指南**——它寫著安全影響、值域與目前生效通道。
這區按下儲存後，CSP 下一次開機會重新驗證 DB 列；驗證成功就同步到該行程的
Settings／env，回頭看那一列的「現在生效」與「來源」是否變成 `db-boot`。
若提醒指出 import-time、其他行程或 interpreter consumer，仍要改 compose／`.env` 的
對應部署通道 → `docker compose -p <專案名> up -d csp` → 再回來確認。
（這一類**改的是 compose 本身**，設定雜湊變了，所以裸的 `up -d` 就會重建容器——
與上一節那種「只動 DB」的改動不同，別把兩邊的命令互換。）

⚠ **這份 runbook 刻意不抄一份「哪一顆對應哪個鍵」的清單。** 對應關係跟著登錄表
（`services/csp/app/services/settings_registry.py`）走，抄第二份就會漂掉，
而漂掉的那一份不會有人發現——那正是這一頁存在要消滅的東西。

> ⚠ 重啟不是成功證據；`db-boot` 來源與最上方的退回警示才是。檔案型設定若開機時
> 已不存在，會退回 env／程式預設並在 banner 列出 key。

## 值域：填不進去不是壞掉

每一顆都有宣告的值域，超出範圍會被 **400 擋下並且不留任何一列**，
錯誤訊息會把合法區間講出來。**擋下來是設計**：值域是防呆生命線，
「從畫面把平台打掛」必須是不可能的，不是「不建議」。

如果你覺得某顆的下界擋得莫名其妙，先讀那一顆的說明——例如告警輪詢週期的下界是 15 秒，
因為**消費端本來就有一個 15 秒的硬樓地板**：填 7 不會讓偵測變密，只會被靜默提到 15。
與其收下一個平台不會照辦的值，不如當場不收。

## 存了但沒生效的三種樣子（照這個順序查）

1. **「待生效」還亮著** → 還沒重建，或用的是裸的 `up -d`（它對只動 DB 的改動是 no-op，
   見上面第 2 步）；若是其他行程／import-time consumer，照該列提醒處理。
2. **那一列寫「存了但讀不回來，永遠不會生效」** → DB 裡那一列的字串現在解不出合法值
   （多半是舊值撞上後來收緊的值域）。重存一次就好，**壞掉的列不會被拿來用**。
3. **來源欄說 `env`／`default`，而你以為 DB 該贏** → 看最上方 banner 的載入失敗／
   退回 key，再檢查該列的值域與檔案是否仍存在。若提醒指出其他行程／import-time
   consumer，依該列的部署通道處理。

## 這一頁不管的事

- **其他服務**（router／ingestion-worker／asr）的設定：這一頁只有 **csp 行程讀得到**的東西。
  OCR 那一組的主要消費者是 ingestion-worker（另一個行程，讀不到 csp 的 DB）；CSP 會同步
  自己的 env，但 worker 仍要走 worker 側部署通道。
- **純 compose 插值**的變數（不進容器 env 的那幾顆）不在頁上。
- **零讀取點的死變數永遠不會出現在這一頁**——頁面上看得到的每一顆，都真的有人讀。
