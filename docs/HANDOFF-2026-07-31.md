## 最該知道的三件事

### 1. 你那句「hi」查出了整條線

你晚上說「好像沒有回覆欸」。查下去是三個缺陷疊在一起:

- 串流聊天的網址被拼成 `/v1/v1/chat/completions` → **每一則訊息都 404**
- 而錯誤發生在串流開始之後,**FastAPI 已經無法回錯誤** → 畫面永遠停住
- 記憶檢索因為寫死的模型名大小寫不符,**每一次都失敗**,只在日誌噴 error

三個都修好了。但更重要的是**為什麼拖那麼久才發現**——見下一條。

### 2. 這個平台有一種固定的失敗形狀:**壞掉但看起來正常**

一夜之間遇到三次,而它們其實是同一件事的三個面:

| | |
|---|---|
| nginx 釘住舊 IP | recreate 任何服務 → 全站 502,容器全綠 |
| nginx 把唯一的後端踢出輪替 30 秒 | 高負載 → 502 洪水,`/health` 還是 10ms |
| **而這兩個都沒被發現,是因為 nginx 的健康檢查是 `nginx -t`** | **那只驗設定檔語法** |

第三點才是根:**一個永遠會過的健康檢查,讓前兩個問題可以無限期存在。**
同樣的病也在別處:agent「測試連線」把「不是 401」都當成通過,而你那台 gateway 先驗金鑰再看路由,
所以連錯誤路徑都回 401。**測試連線給你綠燈,實際每則訊息 404。**

全部修好了,而且健康檢查現在會真的發 HTTP 請求。

### 3. 26 個「按了、沒報錯、什麼也沒發生」的控制項

偶然撞到兩個之後,做了一次三個角度的系統性掃描。最嚴重的一個**不需要任何人做錯事**:

> 管理員點開「可用模型」→ 前端讀取失敗被空的 catch 吞掉 → 視窗照開、每個框都沒勾
> (跟「這個人本來就沒權限」畫面上分辨不出來)→ 管理員勾一個想加的、按儲存
> → 後端**全刪重建**,還把被撤掉的模型從那人**所有 API key** 上移除 → **綠色成功**

網路抖一下,一次正常的管理操作就靜默撤光一個人的權限。已修。清單在 `docs/FAKE-CONTROLS.md`,26 項中 13 項已處理。
