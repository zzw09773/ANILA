## 0. 骨架：出貨日的順序決定了什麼擋 tag

權威順序在 `docs/runbooks/intranet-deployment-tutorial.md:191-196`：

> **① 全部合併收齊 → 打 annotated tag → ② 從乾淨 tag 重建全量（兩道閘門）
> → ③ 演練最終包 → ④ §4.3 必驗項**

這條順序決定了兩件事，而**本文件 2026-08-15 稍早的版本兩件都寫反了**：

- **出貨映像在 tag 之後才存在。** 所以「出貨映像上破窗還在」「出貨包的 `Ref` 是乾淨 tag」
  這類檢查**不可能**是 tag 的前置條件——那會構成一個無法滿足的循環：
  要打 tag 得先有映像，要有映像得先打 tag。它們是 **release gate**。
- **出貨映像是從 tag 建出來的。** 所以任何「必須出現在出貨映像裡」的程式碼包，
  就**必須在 tag 之前合併**，不能標成「不擋 tag」。

> ⚠ **2026-08-15 更正（會改變結論，故留痕）**：舊版 §1 標題是
> 「🔴 擋 tag（**tag 之前必須有結果**）」，其下四項必驗全都要求出貨映像／出貨包上的結果；
> 舊版 §2 標題是「🟡 **不擋 tag**，但必須在重建出貨映像之前落地」，其下是四個程式碼包。
> **兩節的內容各自都是對的，錯的是它們被放在哪一節。**
> 照舊版文字執行，會得到「先建映像再打 tag」——那正是 `§4.2` 機械判準要擋掉的演練包形狀。

🔴 **`Ref` 的意義**：出貨包與演練包長得一模一樣，唯一差別是 `MANIFEST.txt` 的 `Ref`；
describe 形（`vX-N-g<hex>`）／`-dirty` ／裸 hash 一律被 loader 判為演練包並拒載
（`intranet-deployment-tutorial.md:205-212`）。
**打完 tag 之後任何改動＝重新走一次整個程序**（`:193`）。

### 🔴 掃描快照：稽核裁定＝**是 tag 硬閘**（2026-08-15，稽核長）

> **閘門不是「掃乾淨」，是「掃過、對的是那棵樹、而且留得下來」。三個條件缺一不可：**
>
> | # | 條件 | 為什麼 |
> |---|---|---|
> | 1 | **對即將打 tag 的那棵樹**跑（不是三天前的、不是掃完又動過的） | Q54 現有缺口就是「掃過的不是要出貨的那套」——**掃早了等於沒掃** |
> | 2 | **在有網路的機器上**跑，且**在打 tag 之前** | tag 之後回不去；氣隙裡沒有第二次機會 |
> | 3 | **留下可攜快照**（不是線上即時查詢的截圖） | Q54 缺口的另一半。**沒有快照，下次還要再掃一次，而那時已經進氣隙了** |
>
> ⚠ **稽核明確「不要求」掃到零漏洞**——那會變成「把系統越搞越嚴」，而且做不到。
> 👉 **要求的是「每一條發現都有判定」**：真風險／可接受／不適用，各有理由。
> 📌 **這跟 F-10 的形狀完全一樣**：不要求測試全綠，要求**每一條紅都有歸屬**。
> **一份記著「有 N 條已判定風險」的掃描報告，比沒有掃描好無限多；
> 而一份「掃過但沒人看結果」的報告，跟沒掃一樣。**

### 為什麼這四件是**一件**（2026-08-17：**變成五件，第五件不是掃描**）

**P2.6 全項重掃、Trivy OS 層、bandit／semgrep、Q54 的相依套件 advisory 比對——

> **它們只能在有網路的機器上做，而且只能對「即將打 tag 的那棵樹」做。**

所以要問的不是「這幾件各自擋不擋 tag」，而是 **「打完 tag 之後還回得去嗎」——回不去。**
出貨包一旦搬進氣隙機房就沒有第二次嘗試，而掃描必須是**對真正要出貨的那組版本**跑的。

## 2. 🔴 tag 之後在出貨包上驗的（release gate）

**判準**：只能在「從乾淨 tag 建出來的出貨包」上驗；tag 之前這些東西還不存在。

🔴 **失敗了會怎樣，先寫在這裡，因為這就是本節與 §1 分開的全部理由**：
**任何一項不過 → 退回 §1、修、重新合併、**刪掉舊 tag 或**重新打一個 tag、重建全量、重驗。**

⚠ **「刪掉舊 tag 或」這五個字是稽核長要求加的，不是修辭**：
**留著一個沒出貨的 tag，下次就會有人分不清哪一個才是真正的出貨版本**——
而出貨包與演練包本來就長得一模一樣，唯一的差別就是 `Ref`。
`intranet-deployment-tutorial.md:193` 的原話是「此後**任何改動＝重新走一次本程序**」。
👉 **本節沒有「先出貨後補」這個選項**；出貨包是不可分割的一件貨。

### 🔧 插入點與更便宜的做法（幕僚長 2026-08-22 查證後修正原處置）

**審查長問「第 5 段的步驟有沒有空隙可以插這道檢查」——有，而且不必新增程序。**
README 的驗收本來就是四步（`infra/deployment/offline/README.md`）：
```
### 1. 收集兩套 ABI
### 2. 在乾淨、版本相符容器按 service manifest 做安裝驗證   ← 在 python:3.13-slim 裡裝，不是服務映像
### 3. 兩套 ABI 各做一次 --network=none overlay patch drill  ← 已經會用出貨映像重建一張 patched image
### 4. 任何 rebuilt image 都要過兩道交付閘門
```

🔴 **而查完之後，缺口比原本描述的更精確**：
- **第 2 步在 `python:3.13-slim` 裡驗**——**它證明 wheelhouse 內部裝得起來，從沒碰過出貨環境。**
- **第 3 步只驗「被 patch 的那一顆版本變了、服務起得來」**（`README:203`）
  ——**它不驗其他相依有沒有被順手改掉。**
👉 **所以兩步都不覆蓋這一格，而第 3 步是天然的插入點：它已經在用出貨映像重建 patched image。**

**🔴 兩道檢查都要，它們回答的不是同一個問題（審查長 2026-08-22 更正幕僚長的「取代」）**：

| 檢查 | 回答的問題 | 性質 |
|---|---|---|
| **A. drill 的 before/after `pip freeze` 相減** | **「這一次 patch 有沒有造成傷害？」** | 量後果、**抽樣** |
| **B. 每張映像 `pip freeze` vs `<service>.freeze.txt`** | **「約束層跟映像是不是對齊的？」** | 量狀態、**覆蓋** |

🔴 **A 乾淨不代表 B 對齊**，理由在 pip 的行為：
> **`--constraint` 只作用在 pip「決定要安裝」的套件上。已經滿足的相依不會被重裝。**
> **所以一個窄的 patch 可能什麼都不移動——即使 manifest 與映像在二十個套件上不一致。**
👉 **後果**：**drill 全綠，而約束層仍然分歧，等真正需要 patch 一顆牽連較廣的套件那天才爆
——而那一天在氣隙裡，沒有人有第二次機會。**

**B 的成本近乎零**：**凍結前每張映像跑一次 `pip freeze` 與對應 freeze 檔相減，一張映像一條指令，只跑一次。**
**有差就落檔（分成版本漂移／環境差異兩類），不必當場修。**

**A 的做法（加進第 3 步）**：
> **在第 3 步的 drill 裡，對「patch 前的出貨映像」與「patch 後的 image」各跑一次 `pip freeze`，相減。**
> **除了刻意要換的那一顆之外，任何移動 = manifest 蓋掉了映像自己的解析結果。**

**為什麼這個版本更好**：它**直接量到後果**（overlay 實際改了什麼），而不是量兩份清單的差異再推論後果；
**而且它加在一個已經存在、已經會重建映像的步驟上**，不是新增程序。

**⏱ 時機（審查長）**：**不是「第 5 段之前」，是「第 5 段裡面、重產之後、凍結之前」。**
🔴 **理由：現在跑，量到的是一個即將被取代的產物**——第 5 段會重產 wheelhouse，
**拿今天的 wheelhouse 對今天的映像比，結論對出貨的那一份不成立。**

### 🆕🔴 docling 的成本模型從來沒有人量過（2026-08-17，稽核長於 docling 收尾輪查出）

**處理時點：打開 `DOC_PARSER=docling` 之前，而且需要 GPU。** 三個數字都量不到就不要開。

**八輪審查審的是錯誤路徑，沒有人審成功路徑的成本。** 稽核長讀到的三個事實：

```
handlers.py:728 程式自己量過的原生解析   400 頁 33–89 秒、1000 頁 81–103 秒
DOCLING_TIMEOUT_SECONDS 預設              120 秒
arq job_timeout 300 秒 / max_tries 3
```

**docling ＋ layout model ＋ EasyOCR 比原生慢得多——而它存在的理由正是那些掃描件。**
**120 秒很可能低於它真正要處理的那種文件的耗時。**

🔴 **而逾時的後果被這一包改成了 `retryable`**：逾時 → 重試 → 同一份再送一次。
⚠ **GPU 那邊沒有取消**（`run_in_threadpool` 不會因客戶端斷線而停），**被放棄的工作繼續佔著 GPU**。

> **正回饋：逾時 → 重試 → GPU 更忙 → 更容易逾時。**
> 📌 **而前八輪把它的「可重試」一路確認到對——正回饋的每一格都是我們簽過名的。**

**服務端也還沒有排隊**：`/parse` 走 `run_in_threadpool`，**沒有 semaphore、沒有佇列上限**
（`main.py:128` 那個 `threading.Thread` 是暖機不是節流）。**十個人同時上傳＝十份文件同時打一張 GPU。**

**要的不是再一輪審查,是三個實測數字**（都需要 GPU）：
① 典型院內 PDF 的耗時 ② 同時 N 份的退化曲線
③ `reresolve` 一個 500 份 collection 要多久——**它可能根本不能在開著 docling 時跑**。

⚠ **稽核長自陳的邊界**：這條正回饋**是讀碼推論不是實測**，靠三個讀到的事實
＋**一個沒量的前提（docling 比原生慢很多）**。**那個前提若錯，整條不成立。**

### 🆕 重試策略沒有接上 `IngestionError.retryable`（2026-08-17，稽核長於 docling 審查第三輪查出）

**處理時點：打開 `DOC_PARSER=docling` 之後的第一個維護窗**（不是「低優先」，是「有前提的」）。

**查證**（`/usr/bin/grep -rn "\.retryable\b" --include="*.py" services/ packages/`，排除測試與 `retryable=` 賦值）：

```
services/ingestion-worker/.../main.py:20   ← 只是一句註解:「A future Sprint will key retries off
                                              IngestionError.retryable」
packages/anila-core/.../errors.py:75       ← 只是序列化進 dict
main.py:70   max_tries = 3                 ← 無條件三次,不看 retryable
```

**所以 `retryable` 這個欄位今天被寫入、被序列化,但沒有任何重試決策讀它。**

🔴 **這一條的價值在於它修正了一句我們自己寫過的話。** docling 那包的 HIGH 裁定
（v4）寫的是「worker 不重試 → 永久 failed」。**精確的說法是「照樣重試 3 次、3 次都失敗、然後永久 failed」。**
稽核長自陳:**那個用詞讓人以為 `retryable=True` 會改變執行期行為——它今天不會。**

**所以那包修好的與沒修好的要分開講**：

| 面向 | 今天生效嗎 |
|---|---|
| **歸因**——不再把「GPU 主機掛了」說成「你的檔案損毀」，稽核統計分得開 | 🟢 **生效** |
| **可重試性**——`retryable=True` 讓它比 `False` 多得到什麼 | ⚠ **不生效**：兩者都是 3 次 |

⚠ **而 3 次是連續快速重試,蓋不住一次 GPU 主機重開機**（分鐘級）。所以在這條接上之前,
**docling 端點的短暫故障仍然會讓那批文件落到 failed**——只是使用者現在看到的原因是對的。

📌 **不是這包的缺陷**（那條線本來就沒接）,列在這裡是因為
**「錯誤訊息正確」與「系統真的會自己恢復」是兩件事,而我們差點把前者當成後者交出去。**

- **87% 的情況使用者看到的是後端寫好的中文**，難看程度接近零；13% 會出現英文，而那 78 條多半是**內部狀態**，一般使用者碰不到大部分。

- ⚠ **明確不建議逐站點改**：**119 處手改會製造 119 次犯錯機會，去換一個 13% 的呈現問題——那是把系統越搞越嚴的典型形狀。**

**處置＝結構解，不是逐點解，而且可以分期**：

1. **119 個站點全部走同一個抽取器**（`extractError`／`errors.js:14`）→ **改那一個中樞就收斂**，不需要各自被改。
2. 後端明示分類：**使用者該做什麼 → 具名欄位；實作細節 → 留在 `detail`**；前端規則變成「只顯示具名欄位，`detail` 一律進 log」。
3. **先做可見傷害那半**（那 78 條英文中文化或標成具名欄位），**架構那半跟著做，不必趕在 tag 前**。
