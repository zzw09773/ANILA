# 待擁有者裁決(累積中,不擋開發)

> 規則:遇到需要擁有者決定的事,**不停下來等**——記在這裡,用當下最保守/最可逆的假設繼續做,
> 並在該處註明假設。擁有者一次處理完之後,回頭改的成本才是真實成本。
>
> 每一條都寫:**問題／為什麼需要你決定／我目前用什麼假設在做／改變主意的成本**。

## Q1 — P4.3 分享改成「指定的人/單位」

**問題**:①指定到「人」、「單位」還是兩者都要? ②撤銷之後,對方已經開過的內容要不要保留?

**為什麼需要你**:這決定資料模型。只做「人」是一張關聯表;要做「單位」就得接部門子樹展開
(P1.2 已有 `_department_scope_ids`);兩者都要則需要一個多型的授權對象。撤銷語意則決定要不要記
「誰在什麼時候看過」。

**目前假設**:尚未開工,等你回答再開。這是 P4 最後一項,不擋其他包。

**改變主意的成本**:低——現在還沒寫。答完當天可做完。

## Q2 — 要不要有 CI

**問題**:這棵樹 `.github/` 只有一個 PR 範本,**零個 workflow**。`infra/ci/` 有兩支 lint
(含禁簡體那支),但**沒有任何東西會自動跑它們**。

**為什麼需要你**:你已經同意撿回三個把關機制(ORM/PG schema 漂移檢查、WCAG 對比、zh-TW lint)。
但在沒有 runner 的情況下加 gate 等於演戲——沒人會跑。所以真正的問題是「要不要有 CI 本身」。
repo 是 PUBLIC 的、GitHub Actions 可以跑;但開發實際發生在內網氣隙那側。

**目前假設**:先不建 CI,那三個檢查以「可手動執行的腳本」形式撿回,並在 runbook 註明何時該跑。
這樣即使日後決定建 CI,腳本可以直接接上。

**改變主意的成本**:低。腳本先寫好,建 CI 只是加一個 workflow 檔。

**問題**:告警要寄到哪個信箱?內網有沒有可用的 SMTP relay(位址/埠/要不要認證)?

**改變主意的成本**:低。偵測與寄送本來就該分開。

## Q4 — ASR 錄音的治理規則(撿回 ASR 之前必須先定)

**問題**:①錄音檔要不要留存?留多久? ②逐字稿要不要繼承該對話的密等?
③在「機密」對話裡能不能用語音輸入?

**為什麼需要你**:語音是一個**全新的資料入口**,而 ASR 那批程式碼寫在四級分類之前,
當時根本沒有這個問題。這不是技術問題,是規格問題。

**目前假設**:ASR 尚未開工(它還要兩個新服務＋3.1 GB 模型檔,不是今晚的事)。

**改變主意的成本**:中。若決定「錄音不留、逐字稿繼承對話密等」,實作很單純;
若要留存錄音,就多一個受分類管制的儲存體。

## Q5 — P2.7 稽核帳防竄改的做法

**問題**:確認採用「**把稽核表的擁有權從執行帳號 `csp_app` 拿走**」這條路?

**為什麼需要你**:這會動到 `0014` 當初把 public schema 全表擁有權轉給 `csp_app` 的決定
(那是為了讓開機時的 `ALTER TABLE` 能跑)。拿走擁有權就得處理那個衝突。
PLAN 0.4 說資料庫可以重建,現在是做這件事最好的時機——但它是不可逆方向的決定。

**背景**:光加 trigger **擋不住**。在 PostgreSQL,表的擁有者可以刪掉自己表上的 trigger、
再把 UPDATE 權限授給自己。而規格 §8 的威脅模型是「防止 admin 權限人員偷偷做假」,
那個人手上拿的就是這組帳號。雜湊鏈也擋不住(能改列的人就能重算),除非鏈頭存在他碰不到的地方。

**目前假設**:排在 embedding 那包的 migration 之後做,採「擁有權移交 + `csp_app` 只保留
INSERT/SELECT」。若你不同意,明早說,還沒動。

**改變主意的成本**:中——若已經寫進 migration 就要再寫一支反向的。
