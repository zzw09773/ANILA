## 🟢 Q50 — ANILA 該不該把使用者記憶送給「外部註冊的 agent」?(2026-08-12 裁決)

**起因**:2026-08-12 追一個 agent 呼叫失敗時發現的。ANILA 目前會把
**使用者的長期記憶**——偏好、已知事實、過往對話片段(含相似度分數)——
組成一段 `## 使用者背景與過往脈絡`,以 **`messages[0]`、role=system** 送出去
(`services/csp/app/api/proxy.py:309`)。

⚠ **對外部註冊的 agent 也一樣送。** 那個端點的網址是**開發者自己填的**。
也就是說:使用者的記憶會離開平台,去到一個平台不控制的地方。

這一次是院內自己的 ISO42001 服務,沒有外洩問題。但規矩要在**同仁開始掛 agent 之前**定好
——Q49 才剛決定「未來強制同事的 agent 都走平台」,掛的人只會變多。

**要決定的**:

| 選項 | 意思 |
|---|---|
| **A(保守,建議)** | 記憶**只在平台內部模型**使用;送給外部註冊 agent 時**不附記憶** |
| B | 照送,但**在 agent 註冊頁明講**這件事,由註冊者自己負責 |
| C | 每隻 agent 一個開關,由核准者決定 |

⚠ **C 要小心**:那會變成第 13 顆設定,而且是**安全語意**的設定——
正是 Q46 那句「能從網頁動到的安全開關,就是一個等著被動的安全開關」指的東西。

> **擁有者裁決(2026-08-12):採 A。** 記憶只在平台內部模型使用;
> 送給外部註冊 agent 時**不附記憶**。

### 落地(未做)

**現況是 B 的行為**:`services/csp/app/api/proxy.py:309`(另有 `413`、`659`)對 agent 呼叫
也照插記憶塊 → 要把「目標是外部註冊 agent」時的記憶注入拿掉。
這與 `HANDOFF-2026-08-11.md` §六 ① 的記憶塊問題是**同一批檔案**,併入同一包處理,
避免兩包撞 `proxy.py`。⚠ 附帶效果:agent 路徑不再送記憶塊之後,§六 ① 那條
「記憶塊把對方 2000 字元守衛打爆」的鏈條對 agent 就斷了——但**內部模型**路徑的
總量上限仍要做(程式常數,不是設定)。

**落地邊界註記(2026-08-12,第一輪實作審查後補)**:
- 判別子必須是**結構事實**:「出向目標是否為註冊 agent」。**不得綁 `is_internal`
  等可從網頁/批次匯入改動的模型屬性**——第一輪實作就綁了,審查判 CRITICAL:
  那顆旗標的語意是網路可達性(治理中心 checkbox),隱私閘不得被目的是別的事的
  操作靜默翻動;且 `.12` 上的模型按可達性語意很可能標「外部」,正式部署時
  主聊天路徑的記憶會整個靜默停止。
- **對話附件不屬「記憶」**:使用者刻意為該輪附的檔案照現況送出(含外部 agent),
  不在本裁決射程。「非 agent 的外部模型」目前不存在;未來若註冊,記憶要不要跟過去
  **回到本題補裁**,不得由任何既有旗標默默決定。

## 🟢 Q49 — 院內的 agent 必須透過平台呼叫模型(2026-08-11 裁決)

**起因**:擁有者請我實測 agent 計量,結果分兩半:

| 呼叫方式 | 有沒有記用量 |
|---|---|
| **串流** | ✅ 有,`caller_agent_id` 歸屬正確、token 數正確 |

⚠ 而且 `services/csp/app/api/proxy.py:1306-1309` 的註解自己寫著:
「non-streaming agent forwards **don't currently emit a token_usage row at all**
(orthogonal pre-existing gap)」。**UI 聊天是串流的,所以從畫面看一切正常**——
腳本、批次、第三方整合那些非串流呼叫的用量,在帳上完全不存在。

**更根本的一件**:agent **自己直連模型**時(像院內那台 ISO42001 服務),
那些 token 消耗發生在平台外面,**平台看不見也記不到**。
`token_usage.py:35-38` 的註解說明 `caller_agent_id` 涵蓋兩個方向——
其中一個就是「agent 帶著平台發的憑證回頭呼叫 CSP」。機制早就在,缺的是**規矩**。

> **擁有者裁決:「1 要走,未來我也會強制我的同事走。」**
> → 院內掛 agent 的人,**agent 內部要用模型必須透過平台**(用平台發的憑證呼叫 CSP 的 `/v1`),
> 不可以自己直連模型端點。這樣每一筆才有歸屬、有稽核。

### 這條規矩要寫進哪裡

- **開發指南**(治理中心的「開發者 → 開發指南」那頁)——同仁掛 agent 時第一個會看的地方
- **部署文件**——內網上線時的驗收項
- ⚠ 並且要說明**怎麼做**:平台有 `發憑證` 端點,還有「下載平台 CA」與 `anila-verify`
  兩個下載鈕,就是為了讓 agent 端**有正確的做法可用**,不必去關掉憑證驗證。

### 待辦(不擋這條規矩)

🔴 **非串流那條分支要補上寫用量**。在補之前,即使同仁照規矩走,
**非串流的呼叫仍然不會被計到**——規矩與機制要一起才成立。
⚠ 補的時候小心不要與串流那條重複計數。

## 🟢 Q48 — 沒檢索的時候要明講「未查院內規章」(2026-08-11 裁決)

**現象**:擁有者把唯一的規章庫取消標記(07:58),48 秒後問「霸凌者是軍人,她會受到怎樣懲罰」,

**問題在答案本身**:那些內容全部來自模型的訓練知識,而畫面上沒有任何東西說明這件事。

⚠ **這是同一種謊從另一扇門進來**:

## ✅ Q44 — 我們正在用「每個 Dockerfile 的每個 `RUN` 都加一行」去繞開一個**機器層級**的問題(2026-08-10 提出)

**現象**:這台開發機的 Symantec DCS 代理(`sisidsdaemon`)會在**任何**容器啟動當下把自己的
目錄與 pid 檔注入可寫層——包含 build 容器——建完又把 pid 檔刪掉,**layer metadata 還記著它**,
於是 `docker save` 直接失敗。2026-08-10 實測 **7 張映像有 2 張存不出去**;
`embedding-proxy:migration` 也一樣(審查抓到的)。**存不出去的映像不可能交付。**

**我目前在做的假設(最保守、可逆)**:照 08-06 的既有先例,在**每個會出貨的 Dockerfile 的每個
`RUN` 尾端**加 `rm -rf /var/lib/sdcssagent /run/sisidsdaemon.pid`,並加一支守衛測試讓下一個
Dockerfile 不會漏抄。已實測有效(七張映像全部存得出去)。

**但這值得你知道兩件事**:

1. **這是把機器的問題永久寫進交付碼。** 內網那台沒有 DCS,那些 `rm` 在那邊是純粹的噪音;

2. **匯出腳本裡本來就有一個對策,而它可能沒用。**
   `build-and-export-for-intranet.sh` 有 `REBUILD_ON_SAVE_FAIL=1`,說明寫著「存不出去就

   **兩張映像各重建兩次、四次全部仍然存不出去(0/4)**。⚠ 這代表**那個旋鈕的說明可能在

**改變主意的成本**:低。守衛與那些 `rm` 之後要拿掉都是機械工作;真正的成本是**現在不問,

## ✅ Q36 — 要不要加憑證偵測(2026-08-06,當日裁決)

## ✅ Q31 — Router 直答的接地設計(2026-08-05,fable5 裁決,已採納)

> **記錄用,不需要你回答。** 擁有者 08-05 指定要問 fable5,結論如下,已採納為施工規格。

**背景**:Router 直答目前**完全不做檢索**——`collection` 這個字在 Router 三千多行裡出現零次。

⚠ **我原本提的「先分類、再檢索」被否決,理由值得記**:分類的時候還沒看到段落,
模型是在**盲判**「我自己答不答得了」——而「要看到段落才判斷得了」正是這件事的前提。
**那個方案邏輯上不成立,不只是比較貴。**

**成本不是取捨**:嵌入約 50–150 ms,一次完整 LLM 回覆是秒級,差 10–50 倍。
「被派走的查詢白做檢索」的浪費是每題約 20 ms。不值得為它設計任何東西。
模型搬到算力中心之後,LLM 那側只會更貴,差距更大。

**紅線**:Router 的服務憑證**必須 scope 鎖死在那一個集合**。給它一把能搜任意集合的鑰匙,

**雙生分支**:注入點天然只有一個(`:1002` 餵所有路徑),但 **metadata 出口是兩份**
(`:1137` 的 `_merge_anila_meta` 與 `:1862` 的 streaming meta event)。防漂移要三件:

## ✅ Q28 — 附件解析:UTF-16 只支援英數為主的檔案(2026-08-02;**08-03 擁有者追認**)

> **✅ 已答(2026-08-03):「對,先維持」。**
> 契約正式成立,不再回頭做「這是真中文還是亂碼」的判斷——那正是燒掉十三輪的東西。

**裁決內容**:上傳的檔案若是 UTF-16 編碼,**只在「解碼後英數字元超過一半」時接受**;
以中文(或其他非英數文字)為主的 UTF-16 檔案**拒收**,並顯示「請另存為 UTF-8 後再上傳」。
UTF-8 完全不受影響——中文為主的 UTF-8 檔案照收,任何長度、有沒有標點都一樣。

**為什麼要這樣**:這條之前燒了**十三輪**。每一輪的做法都是加一條規則去猜
「這段解碼出來的非英數文字,是真的文字還是二進位亂碼」,然後:

- 猜鬆一點 → 執行檔被當成文章收下並計費(實測 `/bin/ls` 未經修改就通過,計了 2342 個 token)
- 猜嚴一點 → **正常的中文文件被整份拒收**(實測記事本存的中文備忘、你自己 repo 的 `CLAUDE.md`)

兩者是**同一條繩子的兩端**:擋住執行檔的那道門檻,同時在擋中文。

新契約跳出這個迴圈的原因:**它從頭到尾不看非英數的那一半**——不看語言、不看用了幾個
不同的字、不看標點。二進位讀成 UTF-16 幾乎必然滿是非英數字元,所以是**用數的**被擋掉。

**代價**:中文為主的 UTF-16 檔案要重存成 UTF-8。實務衝擊小——Word 與 PDF 走完全不同的
解析器(`DocxParser`／`PdfParser`),根本不經過這條路;記事本存「Unicode」的中文備忘會被拒,
但訊息明講怎麼自救,三秒可解。

**前例**:與你 Q24 對 Big5／CP950 的裁決同一個邏輯——**看得見的失敗,勝過看起來對其實錯的結果**。

**改變主意的成本**:高。不同意就得回頭做「真中文 vs 亂碼」的判斷,那正是燒掉十三輪的東西。

## ✅ Q23 — 串流背壓(2026-08-01,審查抓到;**08-03 裁決:慢的不能拖累**)

> **✅ 已答(2026-08-03):「慢的不能拖累」——慢的使用者不得節流模型。**

> ⚠ **實作注意(這段是我加的,不是擁有者說的)**:
> 本節原本寫的預設是「維持無上限佇列」。那**字面上**符合這個裁決,
> 但它只是把「拖慢別人」換成「吃掉記憶體」——一個卡住的前端會讓整段回應無限累積在伺服器上,
> 壓力大時受害的是**整台**,反而更符合「拖累別人」的定義。
>
> **符合裁決意圖的作法是:有上限的緩衝 + 超過就丟棄或中斷那個慢的連線,而不是不設限。**
> 動工時把這條當驗收條件寫進派工,不要照字面實作。

但副作用是**背壓消失**:客戶端(或 Router)卡住時,agent 不再回壓模型,
**整份回答會先堆進記憶體,而且模型在使用者已經看不到時仍全速燒 token**。

**為什麼沒有當場修**:審查者建議的一行修法(佇列加上限)我試過,
**會讓串流測試整批掛死**——producer 被取消時卡在收尾寫入,取消方跟著卡。
照專案鐵則「審查者給的修法是假設不是解答」,我沒有硬塞一個會死結的版本進去,
改成還原＋在程式碼裡註明,並記到這裡。

**為什麼你可能在意**:這跟計量/額度有關。使用者按停止之後,那次生成仍會跑完並計費。

**選項**:①排一包做對的背壓(消費者要能回報,不是只把佇列變小) ②接受現狀,
在計量那邊改成「以實際送達使用者的量計費」 ③接受現狀不動。

**我的建議**:①,但不急——它不影響正確性,只影響成本與記憶體。

**目前假設**:③,已在程式碼註明限制。

## Q10 — ~~治理中心不在本機這套裡~~ **這條是我查錯,已作廢**(2026-07-31)

**原本寫的結論是錯的。** 治理中心**有**在部署,而且一直都在:
`infra/docker/csp.Dockerfile` 是多階段 build——第一階段用 node 建 `apps/csp-governance-ui`,

csp 掛載 `/assets` 並送出 index.html,nginx 的 `location /` 又 proxy 到 csp。
所以打 `https://<主機>/` 進去的就是它。

**我怎麼會查錯**:去看了 `services/csp/Dockerfile`(那支存在,但**不是** compose 實際用的),
又在 compose 裡 grep 不到「governance」就下了結論——compose 指的是
`infra/docker/csp.Dockerfile`,而那支裡面根本沒有 "governance" 這個字串以外的線索。
擁有者一句「但我有進入 csp 啊」才逼出正確答案。

**教訓**(值得留著):**查部署路徑要從實際跑的容器往回追,不要從 repo 裡「看起來對」的檔案往前推。**
`docker inspect` 看映像、`docker exec` 看檔案實際在不在,比 grep 原始碼可靠。

**真正的狀況**:治理中心的改動要**重建 csp** 才會生效(不是 anila-ui)。今天那個
