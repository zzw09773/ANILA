## Q28 — 附件解析:UTF-16 只支援英數為主的檔案(2026-08-02,已實作,等追認)

**裁決內容**:上傳的檔案若是 UTF-16 編碼,**只在「解碼後英數字元超過一半」時接受**;
以中文(或其他非英數文字)為主的 UTF-16 檔案**拒收**,並顯示「請另存為 UTF-8 後再上傳」。
UTF-8 完全不受影響——中文為主的 UTF-8 檔案照收,任何長度、有沒有標點都一樣。

**為什麼要這樣**:這條之前燒了**十三輪**。每一輪的做法都是加一條規則去猜
「這段解碼出來的非英數文字,是真的文字還是二進位亂碼」,然後:

- 猜鬆一點 → 執行檔被當成文章收下並計費(實測 `/bin/ls` 未經修改就通過,計了 2342 個 token)
- 猜嚴一點 → **正常的中文文件被整份拒收**(實測記事本存的中文備忘、你自己 repo 的 `CLAUDE.md`)

兩者是**同一條繩子的兩端**:擋住執行檔的那道門檻,同時在擋中文。

新契約跳出這個迴圈的原因:**它從頭到尾不看非英數的那一半**——不看語言、不看用了幾個
不同的字、不看標點。二進位讀成 UTF-16 幾乎必然滿是非英數字元,所以是**用數的**被擋掉。

**代價**:中文為主的 UTF-16 檔案要重存成 UTF-8。實務衝擊小——Word 與 PDF 走完全不同的
解析器(`DocxParser`／`PdfParser`),根本不經過這條路;記事本存「Unicode」的中文備忘會被拒,
但訊息明講怎麼自救,三秒可解。

**前例**:與你 Q24 對 Big5／CP950 的裁決同一個邏輯——**看得見的失敗,勝過看起來對其實錯的結果**。

**改變主意的成本**:高。不同意就得回頭做「真中文 vs 亂碼」的判斷,那正是燒掉十三輪的東西。

## Q27 — 端點位址的可見性政策,同一個欄位一鬆一緊(2026-08-01,審查順帶發現)

**⚠ 細節不寫在這裡**:本 repo 是 PUBLIC,而這題會點名尚未修補的位置。

**這裡只講你要決定什麼**:平台有一套「誰能看到端點位址」的授權機制,

但**不是每個介面都套上了**——同一個欄位,在 A 介面被遮成 `<owner-only>`,在 B 介面照原樣送出。

**為什麼需要你**:直覺的修法(「機器看得到、人看不到」)在這裡**行不通**,
我查了才發現:負責分派的 Router **就是靠這個欄位**決定要把請求轉去哪,

所以修法取決於一個你才能決定的問題:**Router 那個帳號要用什麼身分被認出來?**

**我目前的假設**:**維持現狀不動**。因為誤改的後果是全平台分派中斷,
而現況已經跑了一段時間。

**改變主意的成本**:低到中,看你選哪個——最省的選項零程式碼改動(只是指派一張授權),
最貴的要改資料庫欄位加 migration。

**順帶**:PLAN 的 2.4「166 個可定址面逐條複驗 ✅」沒有涵蓋這一類。
那次問的是「這個人有沒有權限碰這一筆」,沒問「同一個欄位在別的面是不是有遮」。

## Q24 — 舊編碼回退鏈(2026-08-01)

**✅ 已答(2026-08-01)**:**內網沒有 Big5／CP950** —— 擁有者查過。

## Q23 — 串流的背壓在 P2.1 W5 之後不見了(2026-08-01,審查抓到,我沒硬修)

**問題**:修「使用者按停止會噴錯」時,把串流主體搬進獨立 Task —— 那個修法是對的,
但副作用是**背壓消失**:客戶端(或 Router)卡住時,agent 不再回壓模型,
**整份回答會先堆進記憶體,而且模型在使用者已經看不到時仍全速燒 token**。

**為什麼沒有當場修**:審查者建議的一行修法(佇列加上限)我試過,
**會讓串流測試整批掛死**——producer 被取消時卡在收尾寫入,取消方跟著卡。
照專案鐵則「審查者給的修法是假設不是解答」,我沒有硬塞一個會死結的版本進去,
改成還原＋在程式碼裡註明,並記到這裡。

**為什麼你可能在意**:這跟計量/額度有關。使用者按停止之後,那次生成仍會跑完並計費。

**選項**:①排一包做對的背壓(消費者要能回報,不是只把佇列變小) ②接受現狀,
在計量那邊改成「以實際送達使用者的量計費」 ③接受現狀不動。

**我的建議**:①,但不急——它不影響正確性,只影響成本與記憶體。

**目前假設**:③,已在程式碼註明限制。

## Q22 — 源碼掃描的兩題(2026-08-01,P2.6 重掃)

完整報告在 [`docs/audits/p26-source-scan-2026-08-01.md`](audits/p26-source-scan-2026-08-01.md)
(**0 CRITICAL／0 HIGH**／3 中／6 低)。中風險裡有兩條**我已經自己修了**(部署旗標的靜默降級、
不驗證的靜態路徑),下面兩條是**真的要你決定**,不是缺陷:

**(a) 產出物(artifact)的寫入面,要不要比照匯出面拒收 agent 憑證?**
匯出面已經明確拒絕 agent 身分,但三個 `/v1` 寫入面(建工作、改工作、新版本)沒有這道檢查,

**所以這條大半已經被關掉**;剩下的是「指名任意使用者」那半。
→ **我的建議**:只有平台自己的內部服務可以指名使用者,agent 一律用憑條裡的身分。

**(b) `service_project_bindings` 這張表要執行、刪掉、還是標成「僅供參考」?**
它存在但沒有任何地方真的拿它做授權判斷。三選一都合理,但**現狀是最糟的**——
看起來像一道門,其實不是。這正是「假控制項」那一類。
→ **我的建議**:標成 metadata-only 並在欄位註解寫明,或直接刪。上線前不要留著看起來像門的東西。

**目前假設**:(a) 等 W2 審查結果確認覆蓋範圍後再補那半;(b) 不動,先記著。

「Router must see the whole answer to decide on DISPATCH」——它必須看完整個回答才知道裡面有沒有
`DISPATCH:` 指令,所以直答路徑是**非串流**呼叫模型、拿到完整答案後,再**假裝**成串流分塊吐出。

對使用者:**盯著空白等完整個生成,然後答案一次湧出**。總時間一樣,但體感比真串流慢很多——
真串流是「第一個字很快出現然後持續」,這是「很久都沒東西然後爆出來」。

**問題**:要不要讓直答路徑真的串流?或在某些情況跳過路由判斷?

**為什麼需要你**:這是**準確度 vs 速度**的取捨,不是工程問題。跳過會讓自動分派變笨,
而自動分派正是這個平台的賣點之一。我不替你決定。

**實測依據**(wt/core-opt 報告):

| | 時間 |
|---|---|
| Router 自身開銷 | 3.7 ms(sk)／6.9 ms(JWT) |
| 使用者實際等待 | **秒級**——幾乎全部在那次路由 LLM |

換句話說:**再怎麼優化程式碼都只是幾毫秒,真正的錢在那一輪 LLM。**

**可能的折衷**(都還沒做):
- 使用者已經用 `@` 明確指定 agent 時 → 不必再判斷意圖
- 同一對話的後續訊息 → 沿用上一則的判斷,除非使用者換話題
- 短訊息(「好」「謝謝」「繼續」)→ 不值得為它跑一輪 LLM

**目前假設**:維持現狀,一則一輪。優化分支 `wt/core-opt` 只動了那幾毫秒,沒碰這個決定。

**改變主意的成本**:低到中。前兩個折衷各是幾十行,第三個要定義「短訊息」的判準。
