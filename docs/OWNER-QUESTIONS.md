# 待擁有者裁決(累積中,不擋開發)

> 規則:遇到需要擁有者決定的事,**不停下來等**——記在這裡,用當下最保守/最可逆的假設繼續做,
> 並在該處註明假設。擁有者一次處理完之後,回頭改的成本才是真實成本。
>
> 每一條都寫:**問題／為什麼需要你決定／我目前用什麼假設在做／改變主意的成本**。

**目前假設**:尚未開工,等你回答再開。這是 P4 最後一項,不擋其他包。

## Q2 — 要不要有 CI

**✅ 已答(2026-07-30 晚)**:**不要 CI**——「對一個人維護太辛苦了」。
→ 那三個把關(ORM/PG schema 漂移、WCAG 對比、zh-TW lint)改做成**可手動執行的腳本**,
並在 runbook 註明什麼時候該跑(例如:改 model 之後跑漂移檢查、改配色之後跑對比檢查)。
不強迫、不擋任何流程;日後若有人力再接上 runner 也不必重寫。


**問題**:這棵樹 `.github/` 只有一個 PR 範本,**零個 workflow**。`infra/ci/` 有兩支 lint
(含禁簡體那支),但**沒有任何東西會自動跑它們**。

**為什麼需要你**:你已經同意撿回三個把關機制(ORM/PG schema 漂移檢查、WCAG 對比、zh-TW lint)。
但在沒有 runner 的情況下加 gate 等於演戲——沒人會跑。所以真正的問題是「要不要有 CI 本身」。
repo 是 PUBLIC 的、GitHub Actions 可以跑;但開發實際發生在內網氣隙那側。

**目前假設**:先不建 CI,那三個檢查以「可手動執行的腳本」形式撿回,並在 runbook 註明何時該跑。
這樣即使日後決定建 CI,腳本可以直接接上。

**改變主意的成本**:低。腳本先寫好,建 CI 只是加一個 workflow 檔。

## Q5 — P2.7 稽核帳防竄改的做法

**⏳ 兩家設計已到齊(2026-07-30 晚)**,全文在
[`docs/designs/p27-tamper-evident-audit-fable.md`](designs/p27-tamper-evident-audit-fable.md) 與
[`docs/designs/p27-tamper-evident-audit-kimi.md`](designs/p27-tamper-evident-audit-kimi.md)。
**在你裁決前不動任何相關程式碼。**

**兩家一致的部分(可以當成已收斂)**:
- 稽核三表的**擁有權從 `csp_app` 收回**,執行帳號只留 INSERT/SELECT
- **開機時的 `ALTER TABLE` 衝突有解**——把那段改用第二個 engine(migration 身分)去跑,
  非稽核表的權限一律不動,爆炸半徑最小
- 做**雜湊鏈**,鏈頭要錨在資料庫之外
- **不要任何每週人工儀式**、不要第二台主機、不要 HSM

**兩家的分歧,這才是你要選的**:

| | fable | kimi |
|---|---|---|
| 鏈的粒度 | **日級** | 每個動作 |
| 熱路徑成本 | **0 ms** | +0.2–0.5 ms/筆 |
| 鏈頭錨在哪 | 嵌進**本來就要交的月報/稽核匯出** | 定期匯出檔 |
| 維運者每月 | 0 分鐘 | 約 5 分鐘 |
| 便宜版 | 未提 | **有**:只做鏈＋錨點、不動權限,約一個工作天 |
| 額外主張 | 順手修掉 `users.py:746`(硬刪帳號會洗掉稽核歸屬,它判定那本身是缺陷) | 明確拒絕拿走維運者的 superuser |

**兩家都講了同一句話,值得你看**:目標是 **tamper-evidence(查得出被動過)** 不是
**tamper-proof(動不了)**。kimi 的原話最直白:「假裝能防持主機者正是舊平台被拋棄的思維」。
對「持有主機的人」而言,任何單機方案都只能偵測不能預防——這是拓撲的物理極限,不是實作不夠好。

**我的建議**:fable 的日級鏈 + 錨進月報,因為熱路徑 0ms 且**不新增任何操作者要記得做的事**;
若你想更快看到東西,kimi 的便宜版一天可交且對「換備份」的防禦與完整版相同。


**問題**:確認採用「**把稽核表的擁有權從執行帳號 `csp_app` 拿走**」這條路?

**為什麼需要你**:這會動到 `0014` 當初把 public schema 全表擁有權轉給 `csp_app` 的決定
(那是為了讓開機時的 `ALTER TABLE` 能跑)。拿走擁有權就得處理那個衝突。
PLAN 0.4 說資料庫可以重建,現在是做這件事最好的時機——但它是不可逆方向的決定。

**背景**:光加 trigger **擋不住**。在 PostgreSQL,表的擁有者可以刪掉自己表上的 trigger、
再把 UPDATE 權限授給自己。而規格 §8 的威脅模型是「防止 admin 權限人員偷偷做假」,
那個人手上拿的就是這組帳號。雜湊鏈也擋不住(能改列的人就能重算),除非鏈頭存在他碰不到的地方。

**目前假設**:排在 embedding 那包的 migration 之後做,採「擁有權移交 + `csp_app` 只保留
INSERT/SELECT」。若你不同意,明早說,還沒動。

**改變主意的成本**:中——若已經寫進 migration 就要再寫一支反向的。
