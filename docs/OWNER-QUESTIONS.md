## Q19 — agent 沒被派工時的身分(2026-08-01)

**✅ 已答(2026-08-01,擁有者裁決)**:**③ 作為架構方向,① 作為身分底座;不採 ②。**

擁有者指出我原本論證的漏洞:**③ 解決的是資料流與操作模式,不是身分驗證。**
平台要推送,仍然必須知道推給哪個 agent、收到的是不是本尊、該 agent 是否已停用、
派工有沒有送達、要不要重推。所以「撤銷清單不再需要」這句**只對短效任務憑證成立**,
長期 agent 身分仍必須有平台端的停用與撤銷。

### 兩種憑證要分開

| | 證明什麼 |
|---|---|
| **Agent 身分**(長期) | 我是哪一個 agent instance |
| **任務憑證**(短效) | 我現在被授權執行哪一項任務 |

### 權限模型

| 狀態 | agent 可做的事 |
|---|---|
| 未派工 | 建立控制通道、heartbeat、接收設定版本、接收派工、回覆 ACK。**不得存取業務資料** |
| 已派工 | 用短效 task token 執行指定任務 |
| 任務結束 | task token 失效,回到僅控制通道權限 |
| agent 停用 | 平台封鎖其公鑰／憑證,禁止新連線與新派工 |

### 憑證設計

**Agent 長期身分**:agent 自己產生金鑰對;私鑰留在 OS keystore／TPM／受保護檔案;
**平台只保存公鑰**;可用 mTLS 或 `private_key_jwt`;必須支援停用與輪替。

**任務憑證**:效期約 5 分鐘;綁 `agent_id` 與 `assignment_id`;
限定 API scope、資源範圍與任務類型;**不允許擴充使用者、不允許任意搜尋資料**;
任務結束不再續發。

### 撤銷的正確範圍

- 短效 task token:原則上不需要 agent 去拉撤銷清單
- **長期 agent 身分:仍必須有平台端停用／撤銷**
- **緊急停止任務:不能只等 5 分鐘過期** —— 要能關閉控制通道、取消 assignment,或 API 端即時拒絕

### 寫進設計文件的結論(擁有者原文)

> 採用「非對稱 Agent 身分＋平台推送＋短效任務授權」模式。Agent 未派工時以本機產生並註冊公鑰的
> workload identity 維持低權限控制通道,只能接收設定、派工及回覆狀態;不得存取業務資料。
> 平台於派工時推送設定並核發綁定 assignment 的短效 task token。短效 token 不要求 Agent
> 定期拉取撤銷清單,但長期 Agent 身分仍須支援平台端停用、金鑰輪替及緊急斷線。

**一句話**:選 ③ 降低系統複雜度,但用 ① 解決 ③ 仍然存在的 agent 身分問題;
不要採用 ② 的共享 `.env` 長期祕密。

### ⚠ 對進度的影響(我要說實話的部分)

今天做完的是**任務憑證那一半**(派工時簽 5 分鐘 JWT、agent 驗簽、任務內回呼複用)。
**身分那一半是一個新的子系統**,不是一包工作:公鑰註冊與輪替、控制通道、推送與 ACK、
heartbeat、停用即時生效、緊急斷線。這比 P2.1 原本的範圍大不少。
**時程建議見 `docs/designs/p21-drop-csk-scope-2026-08-01.md` 的〈Q19 裁決與分期〉。**

## Q18 — 編輯重送會把附件掉在原訊息上(2026-08-01,審查「沒改字可重送」時發現)

**問題**:重送／改字重問走的是 branch:前端送 `apiBranchMessage` 的 payload 沒有附件欄位,
後端 `MessageBranchCreate` 也沒有,而附件是在**上傳當下**綁到原本那則 `message_id`。
所以 branch 出來的新訊息**沒有附件**:同一個 session 裡本地清單上那則使用者訊息立刻少了附件,
之後對它 regenerate 就完全不帶檔案——**模型看不到 PDF 卻照樣回答,畫面上沒有任何提示**。

**這是既有缺陷**(改字重問一直都會掉),但「沒改字直接重送」把這條路從罕見變成常態,所以浮上來。

**為什麼需要你**:正解要動後端契約(branch payload 帶附件 reference、service 端 rebind),
不在已核准的前端包範圍;純前端折衷(讓重送後的訊息不偽裝成「原樣那一則」)體驗又很怪。

**選項**:①上線前排一包後端修正(branch 時附件跟過去) ②純前端提示「此重送不含原附件」
③接受現狀寫進已知限制。

**我的建議**:①。這是「讓人以為發生了什麼、其實沒有」的那一類——使用者以為模型看了檔案。

**目前假設**:③暫不動,重送功能照核准上線;此題只影響帶附件的重問。

**改變主意的成本**:中——後端 schema/service 加欄位與 rebind 邏輯,一包可完成。

## Q10 — ~~治理中心不在本機這套裡~~ **這條是我查錯,已作廢**(2026-07-31)

**原本寫的結論是錯的。** 治理中心**有**在部署,而且一直都在:
`infra/docker/csp.Dockerfile` 是多階段 build——第一階段用 node 建 `apps/csp-governance-ui`,
第二階段 `COPY --from=frontend-build /build/dist /app/frontend-dist`;
csp 掛載 `/assets` 並送出 index.html,nginx 的 `location /` 又 proxy 到 csp。
所以打 `https://<主機>/` 進去的就是它。

**我怎麼會查錯**:去看了 `services/csp/Dockerfile`(那支存在,但**不是** compose 實際用的),
又在 compose 裡 grep 不到「governance」就下了結論——compose 指的是
`infra/docker/csp.Dockerfile`,而那支裡面根本沒有 "governance" 這個字串以外的線索。
擁有者一句「但我有進入 csp 啊」才逼出正確答案。

**教訓**(值得留著):**查部署路徑要從實際跑的容器往回追,不要從 repo 裡「看起來對」的檔案往前推。**
`docker inspect` 看映像、`docker exec` 看檔案實際在不在,比 grep 原始碼可靠。

**真正的狀況**:治理中心的改動要**重建 csp** 才會生效(不是 anila-ui)。今天那個
「權限讀取失敗不開視窗」的修正之所以沒出現,只是因為我在那個 commit 之後只重建了 anila-ui。
