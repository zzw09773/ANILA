**我今晚做了什麼**:**把「給同事」那顆按鈕拿掉了。**
它以前長得能用——輸入帳號、按送出、沒有錯誤——但送出的酬載**根本沒有 `to_user_id`**,
只把名字塞進 note 的自由文字,所以建立的是一筆交給「沒有人」的交接,那位同事永遠收不到。
**靜默成功比報錯危險**,寧可先沒有這顆按鈕。「交給其他助手」不受影響,照常運作。

**選項**:

  跟部門樹一致,而且交接對象本來多半就是同單位的人
- ②全院都找得到,但只回傳姓名與單位,不回傳其他欄位
- ③維持現狀(不開),「交給同事」永久不做,交接只給 agent

**改變主意的成本**:低。前端已經拿掉了,接上去是加一個受限的查詢端點＋把選單加回來。

## Q14 — 記憶的來源歸屬會被覆寫,所以「升密即刪」有一個漏網情境(2026-07-31)

P4.4 已經做好:對話一升密,`conversation_memory_chunks` 與 `user_facts` 同一筆交易內刪掉。
**但 `user_facts` 是 `ON CONFLICT (user_id, key) DO UPDATE`**——同一個 key 先在對話 A 學到、
後來在對話 B 又被萃取一次,那一列的 `source_conversation_id` 就被改寫成 B。
**這時候把 A 升密,刪不到它**,因為資料庫裡已經沒有任何線索指向 A。

**這是既有的 schema 語意,不是這次改壞的。** 要修需要一張「一個事實可以有多個來源」的表＋migration。

**發生機率**:要同一個記憶 key 在兩個不同對話裡各被萃取一次,而且其中較早那個後來升密。
不高,但不是零——「我的單位是 XX」這種事實很容易在多個對話裡重複出現。

**選項**:①現在就補 provenance 表(半天到一天,含 migration) ②上線後再說,先在管理頁讓使用者
自己看得到、刪得掉(那條路已經通了) ③接受。

**我的建議**:②。管理頁的真刪已經可用,而且 4.4/4.5 的設計原則你自己寫過是
「**明示且可檢視,勝過自動且隱形**」——使用者看得到、刪得掉,比多一張表更貼近那句話。

**我的建議**:②。本機的用途是驗證流程通不通,不是驗證中文辨識準不準;
