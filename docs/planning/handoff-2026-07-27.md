## A.10 知識庫產品邊界(使用者當場釐清的判準)

**判準是 provenance 不是 ownership**:在 CSP 建的知識庫不進 ANILALM,**即使是個人
建的** —— 開發者可能是為專案而建。`ingestion_collections.origin` NOT NULL + DB CHECK,
伺服器端指派,路由雙掛載(`/api/ingestion`=csp、`/api/personal`=anilalm),跨面 by-id
回 **404 不是 403**。不是授權控制:同一個使用者、同樣的權限,所以擁有權/clearance/
分級閂鎖全部不動,origin 也絕不進檢索與 RLS 路徑。

⚠ **第一版用 ambient(URL 前綴推導)綁 origin,驗收證明它對前綴外的路徑 fail-open
且無聲**,並實測出兩個活洞(`POST /api/conversations`、`POST /api/tasks` 都吃得下
CSP 來源的 collection id,後者還會餵進來源快照與產出管線)。現行版本改成**解析器
要求顯式 origin 參數**,跨產品的呼叫者必須明寫 `ANY_SURFACE`。

## A.11 這一輪的方法學教訓(會重演,務必讀)

1. **PG 測試的假綠**:`r1_0042` 帶著「不可重放」的缺口被我簽收並 push,因為
   `test_w26_startup_ddl_absorption_pg` 在沒有 DSN 時會自己 skip,而那幾輪驗收
   都沒設。全量報綠時其實有 36 個測試從沒執行過。**驗收 PG 相關工作時,DSN 必須
   指向你自己 migrate 過的庫**,而且這個套件用 **6 個不同的環境變數名**表示
   「拿來測的 PostgreSQL」(`ANILA_TEST_PG_DSN` / `TEST_POSTGRES_URL` /
   `TEST_DATABASE_URL` / `DATABASE_URL` / `ANILA_GATE3_TEST_PG_ADMIN_URL` /
   `ANILA_GATE2_LEDGER_PG_URL`),設一個會讓你以為已啟用。
2. **CI 沒跑過這條分支**:`gate1-ci.yml` 只在 PR 到 `main`/`prod-intranet-card`
   或推那兩條時觸發。本機驗證是唯一關卡 —— 諷刺的是 CI 裡就有一條
   「這批測試全被 skip = 等於沒驗」的守衛,只是沒機會跑。
3. **`heads == ["r1_00XX"]` 這種斷言不要寫**:今天在三個檔案裡各紅一次,紅的
   原因都跟它想守的東西無關。要守的是「鏈沒分岔」+「我的 revision 在鏈上」。
4. **migration 守衛要逐物件、不要早退**:「表存在就 return」能重放但**不能修復**,
   表在索引掉的庫會永久少一個索引,而 drift 判它 STRUCTURAL 硬 fail。
5. **ratchet 可以被造假滿足**:`response_model` 的檢查只看「有沒有宣告」,所以
   在回傳 `FileResponse` 的端點上宣告 `response_model=dict` 就能過 —— 代價是公開
   契約的 200 區塊失去 content。誠實的數字是 95。

  80 字放進**列表**,最容易被截圖的地方);讀取一律落稽核列並記**實際密等**
  (原本只有 `>= 機密` 才記)。抽出 `is_controlled()` 當五個外流面的**單一判定來源**,
  門檻是 `> 無機密`,未知值 fail-closed。`is_publicly_shareable()` 改為委派。

## 2.5 夜間追加:一個**現行**的 legal hold 繞過(不在原計畫裡)

專案記憶裡有一條 2026-07-25 的 CRITICAL:`with_for_update()` 缺 `populate_existing()`
會讓 SQLAlchemy 回傳 identity map 裡的**記憶體舊值** —— 鎖還在,讀到的是舊值,於是
「加鎖重讀再決定」這個動作的全部意義消失。記憶的框架是「工單 G(PR #51)把
`SessionLocal` 改成 `expire_on_commit=False` 才會擊穿」,言下之意本分支安全。

**實測證明那個框架太窄。** `expire_on_commit=True` 只在**自己 commit** 時讓物件過期,
所以「A 先讀列 → B(另一 session)改並 commit → A 未 commit 就加鎖重讀」在預設
`True` 之下同樣讀到舊值。真 PG、兩個獨立 session:

```
不加 populate_existing()   legal_hold_seen=False → 照樣刪除(BUG)
加   populate_existing()   legal_hold_seen=True  → 擋下刪除(正確)
```

`retention_reaper` 的形狀正是這樣(先掃候選、再逐筆加鎖重讀)→ **這是現行的
legal hold 繞過,不可逆刪檔 + 法務合規**,不是等 PR #51 才上膛的潛伏問題。那個旗標
只是放大器。

**已修**:AST 掃出 **76 處**(記憶裡的 77 含一個誤報 —— `session_event_store.py`
本來就有,只是寫在 `with_for_update()` **之前**,鏈上順序不影響語意)。補了 **75 處**,
剩 1 處在 `api/ingestion/documents.py`(W2-11 正在改該檔,刻意跳過)。

**新增的兩道防線**:
- `infra/ci/check_for_update_populate.py`(AST,不是 grep —— 要判斷「**同一條 query
  chain** 上有沒有」;而且往外走的規則必須是「node 是 parent 的 func/value」,寫成
  「parent 是 Attribute 或 Call」會在 `cast(chain)` 這種把鏈當引數的寫法上走到
  wrapper,把整條鏈的名字弄丟 → 誤報)。baseline 只准降。

  它**刻意同時**斷言「不加會看不到」與「加了才看得到」—— 只斷言後者的話,測試無法

### 3.8 我自己建的第二個壞 gate:drift 的 tz 比對

    db_tz = "WITH TIME ZONE" in str(reflected_type).upper()

SQLAlchemy 反射回來的 `TIMESTAMP(timezone=True)` 在預設 dialect 下 `str()` 就是

(不是 53、不是 65),而且**全部是「DB 已經是 timestamptz、ORM 說謊」,零條需要
ALTER TYPE**。抽查 `agents.approved_at`:DB 是 `timestamp with time zone`,ORM 寫
`Column(DateTime)`。

→ 已直接改 ORM 宣告(31 欄 / 11 檔,diff 31 insertions / 31 deletions)。
