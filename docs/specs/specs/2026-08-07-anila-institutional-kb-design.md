# ANILA 直接檢索院內規章知識庫 — 設計

> 2026-08-07。擁有者已逐段裁決；顧問（另一個 fable5 session）已複審並提出兩項必修，皆已納入。
> **這不是新功能，是規格寫了但沒實作的部分**（`SYSTEM-MAP.md` §3 主線圖：Router 判斷
> 「不需要 agent」時「用 general 知識庫 + 模型直接回答」）。

---

## 1. 問題

ANILA（智慧代理平台）**無法檢索 CSP 建立的院內規章**。今天的實況：

- `conversations` 的 `collection_id` **僅限** `origin='anilalm'`，`anila-ui` 傳了會 400
  （`services/csp/app/api/conversations.py:35-39` 的契約註解寫著「anila-ui has no collection concept」）
- `agents` 表 **0 筆**，所以 Router 沒有任何對象可派
- 知識庫 id 2「軍人法規」`origin=csp`、330 chunks、密等無機密——**存在，但聊天視窗碰不到**

規格對這條路的原設計是走 agent：dev 在 MLSteam 部署 agent、在該端的 `.env` 指定 collection ID。
擁有者的反對意見是產品定位問題，不是實作偏好：

> ANILALM 是使用者放自己的文檔（NotebookLM 式）；ANILA 是**智慧代理平台**。
> 院內規章是平台的共同知識，**不該每一份都養一個 agent**。

### 裁決 3 的修訂（2026-08-07，`docs/OWNER-QUESTIONS.md` Q39）

**原句**：「Router 判斷再搜」／「照規格 §3；不是每則訊息都搜」。
**修訂為**：「**檢索照門檻走，掛在答案通道上**」——CSP 在 Router 的**答案通道**呼叫上
**無條件**注入規章檢索，§7 的分數門檻才是擋掉離題回合的那道閘門。

**為什麼原句做不到——時序**：Router 的 LLM 呼叫發生在路由決策**之前**。
`router_server.py:1170` 呼叫 LLM → `:1195` 取出文字 → `:1196` **才從那段文字裡**解析出要不要派工。
**只有一次呼叫，而那次呼叫的產出就是答案。** CSP 看到那通呼叫時，Router 自己都還不知道
會不會派 agent，所以「等 Router 判斷直答之後再檢索」**沒有可以插進去的時間點**。
Task 5 出貨的那個 header 標的是 Router 的**答案通道**，不是一個判定結果
（消費端語意以 `task-5-report.md` §1 為準，**不是計畫的 Interfaces 那行**）。

**擁有者接受的代價**：最後決定派工的回合會**白做一次檢索**（一次 embedding ＋一次向量搜尋，數十毫秒）。
另外兩條路被否決：Router 判定直答後**再發一次**「有依據」的呼叫（每個直答多一趟完整 LLM 往返，
而且第一次的產出被丟掉）；把檢索**移進 Router**（需要一把跨庫讀取憑證——那正是當初選做法 A 的理由）。

⚠ 這個修訂**不改變** §5 的五狀態，也不改變裁決 8（沒搜就不顯示任何標記）：
**預設的單輪派工**走的是 agent 路徑，那條路上沒有規章檢索，**照樣不顯示標記**
（而且路由那一通呼叫拿到的檢索結果會被清掉，不會黏到派工的答案上——已釘測試）。

⚠ **一個例外要記住：多輪合成呼叫。** 派工回合若走多輪（`anila_multi_turn > 1`，
**這個值由 client 控制、沒有上限夾制**），最後那通**合成**呼叫本身就是一條**被標記的答案通道**，
所以**會收到規章注入**。這是刻意的、不是洩漏——**那通呼叫的產出就是使用者讀到的字**，
給它依據才是對的；代價是同一則答案裡混著 agent 的產出與規章來源，**兩種來源必須在畫面上分得出來**。

## 3. 架構

```
使用者在 ANILA 提問
   └─▶ Router 讀意圖
         ├─ 需要 agent ──▶ 既有派工路徑（不動）
         └─ 不需要 agent ──▶ CSP 對話路徑
                              ├─ 伺服器端取出「已標記」的知識庫集合
                              ├─ 逐庫檢索（RLS 要求，見 §4.3）→ 合併 → 分數門檻
                              ├─ 命中內容 + 出處進提示詞
                              └─ 四狀態之一隨 payload 回前端
```

**不動的東西**：agent 派工路徑、ANILALM 的檢索、`conversations.py` 的 origin 守衛
（client 在這條路上**永遠不提名 collection id**，標記集一律伺服器端從 DB flag 選出）。

## 4. 安全邊界

### 4.1 標記本身（collection 層）

`ingestion_collections` 新增 `anila_searchable BOOLEAN NOT NULL DEFAULT false`，migration `r1_0033`
（編號**派工前依撞車檢查表再確認一次**）。

閉合性交給資料庫，不是程式：

```sql
CHECK (NOT anila_searchable OR classification_level = '無機密')
```

這條約束的價值在於**它讓「調高密等但忘了取消標記」變成 UPDATE 失敗**，而不是靜默留下一個
被全院檢索的機密庫。升密的程式必須明確先取消標記——耦合**看得見、會叫**。

⚠ **app 層必須把 CHECK 違反翻譯成人話**。撞到 IntegrityError 500 的人無法自救；
要翻成「此庫已標記為 ANILA 可搜尋，請先取消標記再升密」。**兩層都要，各釘一條測試。**

**誰能標記**：admin only，翻轉寫入稽核帳（它是密等相鄰操作）。
**不可標記**：`origin='anilalm'` 的個人知識庫——個人筆記本變全院可搜不是本功能的本意。

### 4.2 文件密等（顧問發現 1 — 我原本漏了）

**CHECK 只鎖住 collection 那一列，管不到文件。** 一個「無機密」的知識庫裡可以放進一份機密文件，
於是那份文件的內容會被全院檢索到。**真正會外洩的東西在文件層。**

- **閘門（本包做）**：ANILA 檢索路徑 JOIN 文件表，**只取密等為「無機密」的文件的 chunks**。
- ⚠ **這個過濾絕對不能塞進共用的檢索元件**（`pgvector_store.py` / `anila_pgvector.py`）——
  agent 與 ANILALM 路徑檢索機密內容是**合法的**，全域加了就是靜默弄壞別人。**只放在新的 ANILA 檢索路徑。**
- **標記時預檢**：庫內若有高於無機密的文件，標記當下就把話講明。

**擁有者的 OCR/VLM 直覺拆成另一件（不在本包）**：文件匯入時若內文出現「機密」字樣而上傳者標為無機密，
**跳出警示讓使用者確認**——姿態比照憑證偵測那包（偵測 → 警示 → 使用者決定）。
**刻意不當閘門**：漏判是靜默的，而權威答案應該是密等欄位，不是圖片辨識；用還沒驗證過的 OCR 當安全閘門，
是把賭注押在最不確定的環節。

### 4.3 RLS（顧問提醒 — 會靜默出錯）

`document_chunks` 的 RLS 靠 `SET LOCAL anila.collection_id = N` 放行，**是單一 collection 的機制**。
多庫檢索**必須逐庫 `SET LOCAL` + 查詢再合併**。

⚠ 誰要是寫成一條跨庫查詢，資料庫會**靜默**濾到只剩 GUC 指的那一庫——
「搜了、沒命中」的謊就從後門回來，**而且不報錯**。**這條寫進派工 prompt 當不變式。**

### 4.4 權限例外開得多窄

**原句（設計當時的打算）**：現有 `_require_collection_access` 是「admin 或擁有者」，
本包只加一條——**已標記的知識庫，任何登入者可「搜尋」**（不含改名、灌文件、看文件清單、刪除），
等於把程式碼註記的未來功能 `collection_access_grants` 縮成由密等硬保護的特例。

🟢 **實際出貨比這窄（2026-08-07 收尾時核對）：權限例外一條也沒開。**
`services/csp/app/api/ingestion/search.py` **零改動**，`_require_collection_access` 的語意
**未動**——非擁有者打 ingestion 的搜尋／清單／改名／灌檔／刪除端點，照舊全部擋。
全院取得已標記庫內容的**唯一通道是聊天檢索**：`app/services/institutional_kb.py`
（新模組，不經 ingestion 權限層）用**發問者自己的 session 與身分**逐庫查、逐庫套 RLS，
只有 `app/api/proxy.py` 的答案通道與 admin 的 preview 端點叫得到它。
換句話說，「任何登入者可搜」這件事是**伺服器端替他選庫、把段落餵進他自己那一次問答**，
不是把一個端點放寬給他自己打。

⚠ **讀碼的人不要照原句去找那個例外**——它不存在，也**不要把它補出來**。
真正要維護的不變式在本模組內（白名單過濾、逐庫 GUC），不在 ingestion 權限層。

## 5. 誠實：狀態機

**答錯規定比答不出來嚴重**（軍事單位）。五種狀態，全部由**伺服器端從系統狀態導出**：

| 狀態 | 使用者看到 |
|---|---|
| `searched_hit` | 正常作答 + 出處（文件名）；滑鼠移上去看原文泡泡 + 信心分數 |
| `searched_miss` | 明示「院內規章裡沒找到相關條文，以下是模型的一般知識」，**不阻止回答** |
| `search_error` | 明示「規章檢索失敗，這次沒有查到規章」 |
| `partial_error` | 一庫成功一庫失敗（顧問提醒的第五狀態）：明示哪個庫查不到，或整體算檢索失敗 |
| `not_searched` | **不顯示任何標記** |

**兩條硬不變式：**

1. **「沒命中」與「查不了」必須是兩句不同的話。** 昨晚剛修掉的缺陷就是：檢索失敗時對模型謊稱
   「搜尋跑了、沒命中」，模型照著假前提理直氣壯地推理。
2. **狀態由程式產、隨 payload 明帶四（五）值之一，絕不能靠「payload 裡沒資料」表示。**
   （顧問提醒：若第四狀態是「缺席」，渲染管線一壞，**所有答案都會靜默降級成 `not_searched`**
   ——這正是本專案的頭號家賊。）UI 對 `not_searched` 的呈現選擇是「不畫」，
   但那是**有資料背書的渲染決定**，可測、可突變檢查。

**其他必須守的：**
- **空標記集 ≠ 搜了沒命中**：一個庫都沒標時不要顯示搜過。
- 檢索只取 `status='active'` 的庫。
- `searched_miss` 的提示詞要**明令模型以一般知識口吻作答、不得以條號格式引用**
  ——使用者信的是正文不是標記。擋不死，但要擋。

## 6. 同一顆嵌入模型（裁決 7）

不同模型算出的相似度**不能互相比較**；強行混排會給出看似合理但排錯的結果，**而且不報錯**
（昨晚「索引錯配」那包的近親）。且 `embedding_dim` 不同時單一查詢**連算都算不了**——
所以這不是潔癖，是物理限制。

顧問原本傾向用 rank fusion 拆掉這個限制，想通一件事後翻回來支持保留：
**§7 的門檻是分數制的，混模型 = 每個模型一顆校準旋鈕，一人維運養不起。**
同一顆模型 = 一個門檻 = 整套誠實語意保持簡單。

落地要點：
- **在標記時驗**，錯誤訊息給做法（「此庫用 X、已標記集用 Y，請重嵌後再標」）；
  **絕不要在搜尋時才發現**。
- 程式註解記一句逃生門：「**若未來必須混模型：per-collection 門檻 + rank merge**」——記著，不要現在蓋。

## 7. 分數門檻（裁決 9）⚠ 有未定的數字

好消息：`min_score` 機制**本來就有**（`services/csp/app/api/ingestion/search.py:173`），
預設 0 等於不擋。所以這件事是**訂一個數字並接上**，不是發明新機制。

⚠ **那個數字現在還不知道。** `PLAN.md:77` 記著：
> 對真 `nv-embed` 重跑稀疏表單量測——現有數字來自代理模型，**排序方向可信、絕對值與 0.3 地板必須重校**。

也就是說手上的 0.3 是**用替代模型量的**。門檻訂太高會把該找到的擋掉、太低等於沒門檻。

**擁有者裁決（08-07 追加）：門檻是「設定」不是常數，而且要能在前端校準。**

理由是擁有者提的，而且比原設計好：**嵌入模型隨時可能更換，門檻本來就該跟著換**——
寫死在程式裡才是錯的。原本的 §7 留了一個「數字待定」，那是本設計最不誠實的地方：
一個沒人知道值的門檻，等於把校準責任丟給未來某個人，而他也不會知道怎麼量。

**做法（隨本包出，不等設定頁）：**

1. **門檻存 DB、admin 可改、改完立即生效**（不需重啟）。預設先放 0.3 並在畫面上
   **明確標示「未對真模型校準」**，而不是假裝它是已知數。
2. **附一個校準視圖**：輸入一句測試問句 → 顯示前幾名命中的**內容與各自分數** →
   admin 直接看得出「相關的落在哪、不相關的落在哪」→ 把門檻訂在中間。
   **檢索 API 本來就回分數**（`SearchResponse`），所以這是既有能力的呈現，不是新機制。
   換嵌入模型之後重跑一次即可。
3. **更換嵌入模型時提示重新校準**——標記集換模型是已知的「門檻失效」事件。

🔴 **實際出貨與這三點的落差（2026-08-07 收尾時核對）：只出了後端，沒有畫面。**
Task 4 交付的是 `platform_settings` ＋ migration `r1_0034` ＋三個 admin 端點
（`GET`／`PUT /api/institutional-kb/threshold`、`POST /api/institutional-kb/preview`），
**治理中心零改動**。所以第 1 點的「在畫面上標示未校準」現在是 API 回應裡的 `calibrated` 旗標，
第 2 點的校準視圖**沒有被任何 task 承載**，第 3 點的提示也還沒有地方可以顯示。
今天要校準只能打 API（程序：`PUT` 成 0 → `preview` 看分數分布 → `PUT` 成中間值，
因為 preview 會套用目前門檻）。**上線前要嘛補畫面、要嘛把這個程序寫進運維手冊。**

⚠ **這一顆設定是「設定頁」那件大工程的第一個實例**（見 §11 待辦 5）。
它證明「改設定 → 後端立刻吃到 → 不用重啟」這個模式成立（讀取每次真的查 DB，刻意不做快取），
之後做設定頁有已驗過的**後端**樣板可抄，而不是一次搬 41 顆環境變數去賭。
⚠ 但**前端那一半還沒有樣板**——「從畫面改完，檢索行為真的變了」這條驗收
目前只在 API 層成立，畫面層還無從驗起。

## 8. Router 判錯這個洞（設計內建，關不掉）

裁決 3 + 4 的組合有一個結構性後果：**Router 判斷錯（該搜沒搜）→ 不顯示任何標記 →
使用者拿到沒有依據的規定答案，而且沒有提示。** 這個洞關不掉，只能降低與可量測：

> ⚠ **Q39 之後這個洞換了形狀**（見 §2〈裁決 3 的修訂〉）：答案通道上的呼叫現在**一律**檢索，
> 所以「Router 決定直答、卻沒搜」不再發生。**剩下的洞是被判成該派工的回合**——
> 答案由 agent 產生，該路徑沒有規章檢索，使用者一樣看不到標記
> （例外是多輪的**合成**呼叫，它是被標記的答案通道、會收到注入，見 §2 修訂段）。下面三條降低手段照舊適用，
> 其中第 2 條（自救按鈕）在新形狀下更重要，因為它是使用者唯一能把回合搶回直答路徑的動作。

1. **Router 偏向搜**：判錯不搜的代價（軍事單位拿到沒依據的規定答案）遠大於多搜的代價
   （幾百毫秒 + 幾個無關 chunk）。**不確定時一律搜。** 不違反裁決 3，只是把天平壓對邊。
2. **自救通道（擁有者 08-07 裁決：做，採事後版）**：答案下方一顆「**改用院內規章重查**」，
   按下去以同一個問句重跑一次、**強制查規章**（略過 Router 判斷）。

   ⚠ **刻意選事後而非事前**：事前的開關（輸入框旁邊「查規章」）要求使用者**問之前就知道**
   這題該查規章——但他問之前哪知道？事後按鈕出現的時機才對：**使用者是看到答案才知道需要它的**。

   這正是本專案自己的教訓「**被擋的人怎麼自救**」。Router 判錯等於把使用者擋住，
   而原設計沒有給他出路。成本是一顆按鈕 + 重用同一條檢索路徑。
   強制查的那次結果一樣走 §5 的五狀態（可能命中、可能沒命中、可能檢索失敗）。

   **⚠ 08-07 追加裁決（`docs/OWNER-QUESTIONS.md` Q40）：`forced` 的那一回合必不派工。**
   按下「改用院內規章重查」**保證這一輪由直答路徑回答並帶規章檢索**，不會又被交給 agent。
   理由是按鈕的承諾：使用者按的是「查規章」，若拿回來的是另一個 agent 的答案，
   這顆按鈕就是本專案一直在殺的那種假控制項。
3. **可觀測**：Router 的判定（搜／不搜 + 問句）記進現成的推論稽核，試營運期抽樣量測誤判率。
   誤判率高的話，「規章關鍵詞強制搜」甚至「每則都搜」是口袋裡的備用桿——**留著，不是現在建**。

**給擁有者的外部性提醒**：這個功能上線後，使用者對**所有**答案（包括沒搜的）的信任都會上升
——「系統會查規章」的印象不分則。這是功能本身的副作用，值得寫進使用者說明。

## 9. 測試與驗收

每一條保護都必須是**會叫的**，不是靠註解或慣例。

| # | 不變式 | 怎麼證明它是活的 |
|---|---|---|
| 1 | 機密庫**不可能**被標記 | 直接對 DB 下 UPDATE 調高密等（標記還開著）→ 必須**失敗**。測的是資料庫擋不擋，不是應用程式 |
| 2 | CHECK 違反有**人話**與自救指示 | app 層測一條：升密撞約束時回可讀訊息，不是 500 |
| 3 | 沒標記的無機密庫**不會**被搜到 | 建兩個無機密庫、只標一個；結果不得出現另一個 |
| 4 | **機密文件**不會被檢索到 | 無機密庫內放一份機密文件 → 不得出現在結果（顧問發現 1） |
| 5 | 那個過濾**沒有**污染共用元件 | agent／ANILALM 路徑檢索機密內容仍必須成功 |
| 6 | 多庫檢索**逐庫**設 GUC | 跨庫單一查詢的突變 → 必須紅（否則 RLS 靜默濾成一庫） |
| 7 | 非擁有者對已標記庫的 ingestion 端點**照舊全擋**（原句是「能搜、但不能改名／灌檔／看清單／刪除」；實際出貨連「搜」都沒放寬，見 §4.4） | 逐個端點打，全部必須擋；「全院讀得到內容」只在聊天檢索那條路上成立 |
| 8 | 嵌入模型不同的庫不能被標記 | 標記時擋並說明做法 |
| 9 | `origin='anilalm'` 的個人庫不能被標記 | |
| 10 | 「沒命中」與「檢索失敗」是**兩句不同的話** | 把兩者合併的突變 → 必須紅 |
| 11 | 五種狀態畫面上分得出來，且**由 payload 明帶** | 把 `searched_miss` 翻成 `searched_hit` 的突變 → 套件必須紅（csp 沒有突變工具，照 gate6 模式手刻 2–3 個關鍵突變） |
| 12 | 空標記集 ≠ 搜了沒命中 | |

**驗收另派，帶那句**：「**去找這一包自己有沒有長出它要消滅的那個形狀**」
（2026-08-06 至今 16 包 16 中）。本包要消滅的形狀是
**「使用者以為答案有規章依據，其實沒有」**，驗收要特別去找：
有沒有哪條路徑會讓**沒有依據的答案看起來像有依據**。

## 10. 明確不做

- 條號抽取（引用只到文件名；條號是未來的事）
- 整份文件開放閱讀（只開被檢索到的那一段泡泡）
- rank fusion / 混嵌入模型（逃生門記在註解裡）
- OCR/VLM 當密等閘門（改做上傳時警示，**另一件事**）
- 「每則都搜」與「規章關鍵詞強制搜」（備用桿，量到誤判率高才考慮）
- `collection_access_grants` 這個通用跨使用者共享功能（只做密等保護的窄特例）
