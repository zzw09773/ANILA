# 反直覺紀錄

操作 ANILA 時覺得「不該是這樣」的地方都記在這裡。這些是優化目標。
每一條寫：在哪裡、發生什麼、為什麼反直覺、建議怎麼改。修掉的標 ✅ 並寫 commit。

## 2026-09-30　演練機 .35 從零安裝與初始設定

### 安裝

**F-01　安裝目錄要先用 sudo 建，安裝程式不會說**
在哪：第一次安裝。
發生：`/opt/anila`、`/var/lib/anila` 不存在時，一般帳號跑 `anila-update.sh` 會在中途停下。
反直覺：一條指令裝好的承諾，第一步就得先知道要 sudo 建兩個目錄。
建議：✅ `preflight.sh` 會先檢查並印出 sudo 指令（9ee7452d）。✅ 安裝程式在第一次安裝、動任何東西之前，依同樣順序檢查安裝根目錄與 `/var/lib/anila`；不是 root 且目錄不存在或不可寫就停下，並印出這次要改跑的 `sudo bash …/anila-update.sh`（6e45fcc0）。

**F-02　443 被佔用沒有安裝選項**
在哪：共用主機。
發生：只能事先手寫 `/opt/anila/state/.env` 加 `NGINX_HTTPS_PORT`。
反直覺：唯一要問的是站台名稱，但埠衝突也是第一次安裝就可能撞上的事。
建議：✅ 已由 `preflight.sh` 提示（9ee7452d）。✅ 第一次安裝若 HTTPS 埠被佔用且不是 `anila-nginx`，會詢問並把選擇寫進 `state/.env`（600）；沒有終端機就說明怎麼寫 `NGINX_HTTPS_PORT`，更新不會問（6e45fcc0）。

**F-03　密鑰印在畫面上**
在哪：第一次安裝。
發生：管理員與資料庫密碼印到標準輸出；用 nohup 或導到檔案時就留在日誌檔。
反直覺：「只顯示這一次」的東西，實際上會被任何 log 收走。
建議：✅ 密鑰只寫進 `generated-secrets.txt`（600），畫面只印路徑與 `sudo cat`，標準輸出與標準錯誤都不印值（6e45fcc0）。

**F-04　失敗的第一次安裝在 operations.log 記成 failure，重跑成功後沒有說明兩者關係**
在哪：第一次安裝失敗後重跑。
反直覺：看 log 會以為曾經壞過一版。
建議：✅ 同一個目標版本的上一筆是失敗時，成功紀錄會註記「接續上次未完成的安裝」或「接續上次未完成的更新」（6e45fcc0）。

**F-05　`csp-credential-dirs` 在 `docker ps -a` 顯示 Exited**
在哪：安裝後檢查容器。
反直覺：看起來像服務掛了，其實是做完就結束的初始化。
建議：✅ 服務名稱維持 `csp-credential-dirs`，compose 加上 `anila.oneshot=true`；安裝成功會說明這個初始化工作已正常結束，INSTALL.md 改看運行中的容器（6e45fcc0）。

### 登入

**F-06　管理員帳密登入要兩個動作才看得到欄位**
在哪：`/login`。
發生：要在網址加 `?show_alternatives=1`，再點「其他登入方式」，帳號密碼欄位才出現。
反直覺：卡片壞掉時唯一的回頭路，藏在兩層後面，而且網址參數沒有任何畫面提示。
建議：保留隱藏（避免同仁誤用），但參數要有文件以外的線索，或只要一個動作。
✅ 已改：登入頁一律顯示低強調的「其他登入方式」，點一次就展開帳密，`?show_alternatives=1` 仍會預先展開；連結看得到不改伺服器規則，card-only 的帳密登入仍只放行擁有者（ab03dca9）。

**F-07　開發機與正式機的登入頁長得不一樣**
在哪：開發機 `https://127.0.0.1/login`。
發生：開發模式直接顯示帳密欄位，正式姿態要先點「其他登入方式」。
反直覺：在開發機練熟的步驟，到正式機不一樣。
決定（2026-10-01 擁有者）：刻意如此，不改。開發機與正式機本來就是不同姿態。

**F-08　管理員登入後停在治理中心，治理中心沒有進 ANILA 的入口**
在哪：登入後落點。
發生：管理員、開發者、單位管理員落在治理中心；頁面上找不到去 `/anila/` 的連結。
反直覺：平台本體是 ANILA，管理員自己也要用，卻只能手打網址。
建議：所有人登入後進 ANILA；治理中心頂端放「前往 ANILA」。
✅ 已改：沒帶 `next` 時一律進 `/anila/`；治理中心頂端加「前往 ANILA」；單位管理員在 ANILA 也看得到治理中心入口（原本只給擁有者、管理員、開發者，改落點後單位管理員會回不去）。

### 初始設定

**F-09　私有 IP 的模型要兩道開關，錯誤訊息是英文**
在哪：註冊模型、外部服務。
發生：`.env` 的 `ANILA_ALLOW_PRIVATE_ENDPOINT=1` 已開，註冊仍被拒：「endpoint_url host '172.16.120.35' is a private (RFC 1918) IP. ANILA_ALLOW_PRIVATE_ENDPOINT must be on, and the host must be listed in the console trusted hosts.」要先到「信任主機」加 IP。
反直覺：內網的模型本來就全在私有 IP，這是每次安裝必經的一步，卻要從英文錯誤訊息倒推。訊息也沒說哪一道已經開了。
建議：訊息改中文、只講缺的那一道，並附「前往信任主機」連結；或在註冊模型的表單內直接加入信任主機。
✅ 已改（3bc1029f）：私有 IP 拒絕改為只講缺的那一道，缺信任主機時回 `host_not_trusted`，註冊模型與外部服務表單可加入該主機後重試。

**F-10　指定主路由前要先給全院授權，錯誤訊息沒說在哪裡給**
在哪：模型角色 → 主路由。
發生：「全院預設必須具有有效的全院授權」。角色頁的「授權給全院」只能對「已經擔任該角色」的模型用，而主路由正卡在還不能擔任，要改去模型的授權設定。
反直覺：先有雞還是先有蛋。指定主路由本來就意味著全院要能用。
建議：指定主路由時一併建立全院授權（寫稽核），或在錯誤訊息旁直接提供「授權給全院並指定」。
✅ 已改（3bc1029f）：能管理授權的人指定主路由時，同一筆交易會建立全院授權並寫稽核；沒有權限時改提示到模型的授權設定加入「全院」。

**F-11　改了語音位址，閘道一分鐘以上還在用舊位址；「探測」回傳成功但狀態是「未知」**
在哪：外部服務 → 語音。
發生：PUT 後按探測，畫面狀態仍是 unknown；asr-gateway 的 `/asr/health` 仍顯示舊的 `decode_url`。
反直覺：按了探測卻不知道結果，也不知道新設定何時生效。
建議：探測同步回報結果；存檔後通知閘道立即重讀，或畫面寫明「約 N 秒內生效」。
✅ 已改：探測在請求內打完並寫回健康或失敗原因，畫面同步顯示；語音存檔後寫「語音閘道約 N 秒內套用新設定」，N 取閘道重讀間隔，不新增未認證的重讀端點（ab03dca9）。

**F-12　API Key 與外部服務憑證只寫不讀，無法從另一套環境搬設定**
在哪：從開發機照抄設定到新環境。
發生：docling 的憑證在開發機讀不出來，要去模型主機的容器環境變數找。
反直覺：這是對的安全設計，但「照某台的設定再做一台」沒有路。
建議：提供設定匯出（不含密鑰、標出哪些要另外填）與匯入。
✅ 已改（89c2c5ac）：擁有者與管理員可從平台設定匯出不含金鑰的設定檔，匯入先試算再套用；缺金鑰的項目會建立並標成「需另外填入金鑰」。

**F-13　儀表板「模型 1/1 健康」但模型頁寫「尚未註冊模型」**
在哪：全新安裝的儀表板。
發生：平台自己的 `anila-router` 入口被算成一個模型。
反直覺：兩頁對「有沒有模型」說法相反。
建議：儀表板不把平台入口算進模型數，或另列。
✅ 已改（3bc1029f）：健康總覽的模型數排除 anila-router；一台都沒登錄時儀表板寫「尚未註冊模型」。

**F-14　`/api/health` 回 `200 text/html`**
在哪：安裝後用 curl 檢查。
發生：不存在的 API 路徑被前端接住，回首頁。
反直覺：看起來像健康檢查通過。
建議：`/api/*` 未命中時回 404 JSON。
✅ 已改：未命中的 `/api/*` 由 CSP 回 JSON `{"detail":"Not Found"}`，不再掉進 SPA 的 index.html；nginx 的 `/api/` 維持轉發、不用 try_files（ab03dca9）。

**F-15　ANILA 裡的「治理中心」入口藏在「平台入口」彈窗裡**
在哪：ANILA 側欄。
發生：管理員要先點「平台入口」，彈窗裡才有「治理中心」。
反直覺：所有人登入後都先進 ANILA，管理員要回治理中心卻要多一層、名稱也看不出來。
建議：管理員身分時，側欄或頂端直接放「治理中心」。
✅ 已改（9436dfce）：看得到治理中心的身分（含單位管理員）在側欄直接看到與「平台入口」相同網址的「治理中心」。

## 2026-10-01　演練機 .35 第一次「更新」（09.30-14 → 10.01-1）

建議：✅ 根因已修（5896e069）。✅ 自動回復結束而入口沒開時，會明說「入口未開啟，同仁目前連不上」，並印出用實際路徑與專案開啟 nginx 的指令（6e45fcc0）。

在哪：第一次安裝用一般帳號成功，之後的更新。
發生：服務帳號的資料目錄一般帳號讀不到，更新前的檔案快照做不成。

發生：從排程或遠端無終端機執行時，問句讀到空值，直接取消。

建議：✅ 沒有公告且沒有終端機時，會說明已取消、請先貼公告；排程可設 `ANILA_UPDATE_ASSUME_YES=1` 跳過這題（6e45fcc0）。

**F-22　更新程式的錯誤不能靠新出貨包修好**
在哪：`sudo bash /opt/anila/anila-update.sh 新包.tar.gz`（UPDATE.md 寫的做法）。
發生：整個更新由主機上已安裝的舊 `anila-update.sh` 執行；新包附的腳本要等更新做完才換上。10.01-1 修的三個問題都在更新流程裡，照文件跑會用舊腳本再失敗一次。演練改成先解開新包、執行包裡的 `anila-update.sh`。
反直覺：裝了「修好更新程式」的新版，下一次更新才吃得到修正。
建議：✅ 已安裝的更新程式核對清單後，把工作交給新出貨包裡已核對過的 `anila-update.sh`，並避免再交一次；UPDATE.md 改回 `sudo bash /opt/anila/anila-update.sh <新包.tar.gz>`，兩種執行方式都可以（6e45fcc0）。

**F-23　公告的「登入頁公開」不會出現在登入頁**
在哪：治理中心「公告橫幅」→ 勾「登入頁公開」。

反直覺：勾選名稱說「登入頁公開」，實際只有剛註冊、等核准的人看得到。更新前想讓還沒登入的同仁知道，沒有辦法。
建議：登入頁上方顯示公開公告；或把勾選改名為「顯示在等待核准畫面」。
✅ 已改：登入頁上方顯示勾了的公開公告，等待核准畫面仍用第一則，勾選改名「登入頁與等待核准畫面都顯示」；anila-shell 與 anilalm 沒有自己的登入頁，未登入會導向治理中心 `/login`（ab03dca9）。

## 2026-10-01　出貨版本先後

**F-26　換一個目錄打包，版本號從 1 再算，更新也不比較先後**
在哪：`build-release.sh` 的 `dist/releases/seq/<日期>`，以及 `anila-update.sh` 的更新路徑。
發生：版本是 `YYYY.MM.DD-N`，N 只看該輸出目錄的計數。從另一個檢出打包，N 從 1 開始，主機上已經是 `2026.10.01-2`。更新沒有比較先後，會裝上較舊或相同的版本，畫面仍像更新成功。
反直覺：號碼看起來是全域的，其實只在那個輸出目錄裡遞增；裝舊版也不會被擋，回到舊版應該走 rollback。
建議：✅ 更新在核對清單之後、取鎖與停服務之前比較日期與序號：相同拒絕「這一版已經安裝了（X）」（`ANILA_UPDATE_REINSTALL=1` 可重裝），較舊拒絕並請改走 rollback（`ANILA_ALLOW_DOWNGRADE=1` 可放行）。打包時 N 也看輸出目錄裡已有的 `anila-YYYY.MM.DD-*`，並提醒版本號只在這個目錄遞增。預檢讀得到已安裝版本時會印出先後。（73318546）

發生：已安裝的更新程式印出「交給新出貨包的更新程式 2026.10.01-4」之後，新程式立刻拒絕：「拒絕操作：從工作樹對 compose 專案 anila 停服務或動資料庫…」。壓縮檔先解開到 `${TMPDIR:-/tmp}`，新程式不在安裝根目錄裡，防護把它看成原始碼工作樹。同一包先解開到 `/opt/anila` 再跑就不會。
反直覺：文件寫的 tar.gz 更新，清單核對過、工作也交出去了，卻在動服務之前被自己的防護擋下。
建議：✅ 壓縮檔的交接暫存改放在安裝根目錄的 `.handoff`（0700，root 執行時擁有者是 root），成功、失敗與中斷都會清掉，超過一天的舊暫存在開始時清掉；安裝根目錄不可寫就拒絕，不改解到別處。工作樹防護沒有放寬。（bf29d081）

## 2026-10-02　出貨包裡的檔名會被 tar 當成選項

**F-28　核對清單之前，出貨包內的路徑直接交給 tar**
在哪：`anila-update.sh` 的清單核對、`release-lib.sh` 的 `release_peek_bundle_version`（以 root 執行，而且在核對 SHA256 之前）。
發生：從 `tar -tzf` 讀出的成員名稱原樣放進 `tar -x… "$成員"`。資料夾若取名為 `--to-command=…` 之類，tar 會把它當成選項解析；實測舊程式出現「只允許一個 --to-command 選項」，代表名稱確實被當成參數。能不能進一步執行指令取決於 tar 版本與選項，但不該把出貨包內容當參數。由 GPT 接手時發現（2026-10-02）。
反直覺：出貨包的信任是在核對之後才成立，核對本身卻先用了出貨包裡的名字。
建議：✅ 已改（commit 待補）：路徑每一段只接受英數、點、底線、連字號且不能以 - 開頭，不合規的成員直接忽略；從出貨包讀出的成員名稱一律放在 `--` 之後交給 tar。測試 `test_tar_member_names_cannot_inject_options` 在舊程式上失敗。
