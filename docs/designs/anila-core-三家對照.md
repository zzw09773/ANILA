# anila-core 三家意見對照(2026-07-30 夜)

> fable / kimi / GLM-5.2 各自獨立回答同一份問題,**互不知道對方寫了什麼**。
> 全文分別在同目錄的 `anila-core-opinion-{fable,kimi,glm}.md`;優化實測在 `anila-core-optimisation-report.md`。
> 分支 `wt/core-opt` **刻意沒有 merge**——擁有者要親自體驗過才決定。

## 先講一件事:我問錯了,三家有兩家糾正我

我原本告訴擁有者「**每則訊息付兩輪 LLM**」。**那是錯的**,fable 和 kimi 各自獨立指出,
我查證程式碼後確認他們對:

| 情況 | LLM 輪數 |
|---|---|
| Router 自己答 | **一輪**——那一輪的輸出**就是**答案 |
| 派給 agent | 兩輪(判斷 ＋ agent) |

**但真正的代價不是輪數,是「不能串流」。**
`router_server.py` 的註解自己寫著:「Router must see the whole answer to decide on DISPATCH」——
它必須看完整個回答才知道有沒有 `DISPATCH:` 指令,所以直答路徑是**非串流**呼叫模型、
拿到完整答案後,再**假裝**成串流分塊吐出。

對使用者:**盯著空白等完整個生成,然後答案一次湧出**。總時間一樣,體感差很多。

## 三家的核心立場

| | fable | kimi | GLM-5.2 |
|---|---|---|---|
| **每則跑 LLM 路由對不對** | **對**——直答本來就只有一輪,只有 dispatch 多付一短輪 | **對**——但決策前該先看**實際 dispatch 率**,不要假設全體兩倍 | **要改**——加規則式捷徑跳過 sentinel,LLM 只當模糊情況的後備 |
| **該先做什麼** | 先親試,再 merge,但**先修兩個錯的預設值** | merge OPT-1/3/4/5/6,**砍 OPT-2**;同批修記憶體洩漏 | 規則捷徑＋**先上路由可見性**才看得到誤判率 |
| **JWT 快取的撤銷風險** | 被高估——CSP 每請求驗 `token_version`,router 原樣轉發 JWT | 同上,窗口只剩「讀自己的 session state」,危害≈零 | 要求說清楚失效故事 |
| **成本估計** | — | — | 約一週,常見情況少約 50% 延遲,維運者每週 ≈0 |

**三家一致**:JWT 指紋快取的撤銷疑慮**是我多慮了**——被撤銷的人在 sentinel 那一跳就會被 CSP 擋下,
因為 router 是把原始 JWT 轉發過去、CSP 每次都查資料庫驗 `token_version`。

## 各自獨有的發現(這是分三家問的價值)

**kimi 獨家** — `RemoteAgentRegistry` **記憶體無界成長**:以 `sha256(token)` 為鍵、零淘汰機制,
JWT 每 60 分鐘輪替 → 三千人每小時新增三千個永不釋放的條目。
我已實地驗證(全檔 `pop`/`del`/`maxsize`/LRU 命中數 = 0),記為 **PLAN X.8**。
kimi 的原話:「整個區域唯一隨 uptime 惡化且目前無人認領的缺陷」。
**三家看同一份程式碼,只有一家看到。**

**fable 獨家** — 優化分支自己引入的兩個問題:
① `http_pool.py:53-56` 的 `max_connections=100` ＋ `pool=5.0` 逾時,
在三千人尖峰會**製造原本不存在的 PoolTimeout 失敗**——它稱之為「本包唯一錯的預設」;
② OPT-4 讓一個壞掉的 JWT 汙染全域 `_last_refresh_error`,**滲進別人的 trace**。

**GLM 獨家** — 把「改路由」和「看得到誤判」綁在一起:先上路由可見性,
才有辦法知道規則捷徑有沒有判錯。**沒有可見性就調不動參數。**

## 我的建議(僅供參考,你決定)

1. **先修 fable 指出的那兩個預設值**——那是我們自己在優化過程中新增的風險,不修就 merge 等於用新問題換舊問題。
2. **X.8 記憶體洩漏獨立成小包**,不要混進 `wt/core-opt`——那條分支你還沒體驗過,混進去會讓「這條是誰造成的」說不清。
3. **路由要不要改,先看 dispatch 率**(kimi 的建議最務實)。如果實際上九成訊息都是直答,
   那 GLM 的規則捷徑收益有限;如果一半在 dispatch,那就值得。**但我們現在量不到,因為沒有可見性**——
   所以 GLM 那條「先上可見性」其實是三家建議裡最先該做的。
4. **真串流那件事**(直答不能邊生成邊顯示)三家都沒特別著墨,但我認為那才是使用者最有感的,
   已記進 `docs/OWNER-QUESTIONS.md` Q7。
