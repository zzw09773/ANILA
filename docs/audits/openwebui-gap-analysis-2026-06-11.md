# Open WebUI vs ANILA UI 功能差距分析

> 2026-06-11 · 方法:98 個平行 agent 三階段(8 域掃描 open-webui 原始碼 + 2 agent 全讀 ANILA UI 8,762 行 → 逐域差距分類 → 對 ANILA/ANILALM/CSP 源碼反向驗證每項宣稱)。共掃描 220 個 open-webui 功能,80 個高相關候選經對抗驗證:39 確認缺失、39 部分存在、2 被推翻(其實已有)。

> 分類基準:`missing`=確缺 / `partial`=有但較弱 / `covered_elsewhere`=CSP 主控台或 ANILALM 已涵蓋 / `irrelevant`=需外網或違反 air-gap(23 項,如雲端 TTS、社群分享、web search)。relevance 1-5 = 對軍方內網使用者的日常實用價值。


## 確認缺失(real_gap)

### [5分 / M] Admin announcement banners
- **域**: collaboration-admin-ux | **狀態**: missing
- **說明**: 管理員維護多則橫幅公告(info/warning/error/success、Markdown、拖曳排序、可記住關閉)。ANILA 聊天端與 CSP 管理後台都沒有任何對聊天前端的公告推播機制。
- **評估**: 內網環境停機維護通知、資安宣導、使用規範公告是軍方剛需且完全離線可用;目前唯一管道是口頭/公文,成本極高。建議編輯端做在 CSP 管理後台(Vue),聊天端只負責拉取顯示;effort M 是因為橫跨兩個 app(CSP CRUD + config API + 前端渲染)。
- **驗證證據**: Confirmed absent in all three apps. (1) ANILA UI chat frontend: grep for announce|banner|公告|bulletin|notice|broadcast|motd over /home/aia/c1147259/ANILA/ANILA_UI/anila-ui/src yields only src/app.jsx:465 (comment about the per-conversation classified-warning banner, a security-classification UI, not announcements) and app.jsx:1158 (router handoff rows). The only banner-like primitive is src/confirm.jsx — a transient toast stack (toast(message,{tone:"info"|"error"|"success"}), auto-dismiss, code-triggered only); no admin source, no persistence, no Markdown, no ordering, no remembered dismissal. src/runtime/api.js and src/data.jsx expose no announcement-fetch endpoint. (2) CSP admin console: /home/aia/c1147259/ANILA/myCSPPlatform/frontend/src/views/ contains no announcement view; AlertsView.vue is internal ops anomaly alerts (ack/resolve) for admins, not user-facing announcements; all "banner" hits (ServiceClientsView.vue:85, DeveloperAgentsView.vue:126/266) are one-time secret-token or pending-agent admin notices. Backend /home/aia/c1147259/ANILA/myCSPPlatform/backend/app/api/ has no announcements route (agents/alerts/conversations/users/... only); backend banner mentions (api/conversations.py:107, models/conversation.py:37) are the classified-conversation banner. (3) ANILALM banner hits (src/workspace/WSSidebar.tsx:47,215, src/routes/DashboardPage.tsx:99) are inline error banners replacing window.alert. No announcement push mechanism exists anywhere; the feature is fully offline-capable, so it is a genuine missing chat-UX gap (existing toast tones and banner-rendering patterns would be reusable building blocks for implementing it).

### [5分 / S] Stop generation
- **域**: chat-messages | **狀態**: missing
- **說明**: Send button becomes Stop while streaming; cancels backend task and keeps partial output.
- **評估**: Verified by grep: ZERO AbortController/abort usage in src — once a stream starts the user cannot cancel it. With multi-second agent handoff chains and long Gemma generations this is the most painful daily gap in the whole domain. Client-side fix is small: pass an AbortSignal into streamChatCompletion's fetch (runtime/sse.js), keep accumulated partial text, persist it. Server-side task cancellation is a nice-to-have second step; client abort alone delivers most of the UX value.
- **驗證證據**: Confirmed absent in ANILA UI chat runtime. (1) src/runtime/sse.js: streamChatCompletion (lines 59-164) and streamSessionAnswer (lines 282-345) call fetch with no `signal` option and expose no AbortSignal parameter; the reader loop runs until server close — no transport-level abort path. (2) src/app.jsx: sendMessage (line 986) sets `streaming: true` (line 1018) and awaits streamChatCompletion (line 1049) with no AbortController at any of the 4 call sites (821, 1049, 1238, 1452). (3) src/chat.jsx lines 1112-1127: the Composer button always renders IconSend ("送出") and never toggles to Stop; the UI is stream-aware (msg.streaming disables Regenerate with "回應產生中…", lines 555-562) but offers no stop affordance. (4) grep for AbortController/.abort(/signal: across anila-ui/src returns zero hits; runtime/api.js has no cancel endpoint. The `anila.interrupt_requested`/InterruptCard machinery (agentic.jsx) is agent-initiated HITL pause, not user-initiated stop. Not covered elsewhere for this surface: ANILALM/src/workspace/WSChat.tsx lines 98/277/409 do implement a stop button with AbortController ("the user's stop button can interrupt search OR streaming OR persistence"), but that is the separate ANILALM workspace chat — it does not stop ANILA UI chat streams. CSP console has no chat. Air-gap compatible feature (pure client + Router cancel), genuinely usable; in-house ANILALM pattern shows the client half is easily portable, though backend task cancellation would also need a Router endpoint (none wrapped in runtime/api.js).

### [5分 / S] IME-safe Enter handling + Ctrl-Enter-to-send option
- **域**: chat-input | **狀態**: missing
- **說明**: Guard Enter against CJK IME composition (isComposing / keyCode 229, Safari compositionend workaround) so confirming Zhuyin/Pinyin candidates does not send the message; optional ctrlEnterToSend setting.
- **評估**: Verified live bug-grade gap: chat.jsx lines 825/842 fire submit()/insertMention() on bare Enter with no e.nativeEvent.isComposing check. Every ANILA user is a zh-TW IME user, so accidental sends mid-composition hit daily. Fix is a few lines plus composition-event state in the existing onKey handler. Highest value-per-effort item in this domain.
- **驗證證據**: Confirmed absent in ANILA UI. (1) Main chat composer keydown handler at /home/aia/c1147259/ANILA/ANILA_UI/anila-ui/src/chat.jsx:811-846 (bound to the textarea at chat.jsx:1033): `if (e.key === "Enter" && !e.shiftKey) { e.preventDefault(); submit(); }` (lines 842-845) — no `isComposing` check, no `keyCode === 229` guard, no compositionstart/compositionend handling anywhere in src (grep for "composing|composition|keyCode" across anila-ui/src returns zero hits). For zh-TW Zhuyin/Pinyin users, pressing Enter to confirm an IME candidate will fire submit(). The mention-menu Enter capture (chat.jsx:825) has the same flaw. (2) No ctrlEnterToSend / enterToSend / sendOnEnter setting exists anywhere in anila-ui/src (grep zero hits); the only Ctrl+Enter binding is in the message-EDIT textarea (chat.jsx:359, `(e.ctrlKey || e.metaKey) && e.key === "Enter"` to save an edit, hint text at chat.jsx:385) — a different feature, not a configurable send mode for the composer. Notably, the sibling app ANILALM already guards correctly at /home/aia/c1147259/ANILA/ANILALM/src/workspace/WSChat.tsx:402: `if (e.key === 'Enter' && !e.shiftKey && !e.nativeEvent.isComposing)` — proving the team considers this necessary for their zh-TW users, yet the main chat UI (where chat UX is squarely in scope, not covered_elsewhere) lacks it. CSP console has no such handling either. Highly relevant gap given the all-CJK (Zhuyin/Pinyin IME) target user base.

### [5分 / S] Banner display with per-user dismissal memory
- **域**: collaboration-admin-ux | **狀態**: missing
- **說明**: 橫幅顯示在聊天頂部,使用者關閉後以 localStorage dismissedBannerIds 記住,導航時重新抓取最新橫幅。ANILA 聊天 UI 完全沒有此顯示面(grep app.jsx/chat.jsx 無 banner 渲染)。
- **評估**: 與上一項同套機制的前端半邊,單獨看實作成本很低:ANILA 已有 ReactMarkdown pipeline 可重用(React 預設 escape,無需額外 DOMPurify)、已有 localStorage 慣例(anila-folders)。公告編輯端就緒後,顯示端一兩天可完成。
- **驗證證據**: 確認此功能在三個前端與後端皆不存在,主張成立。逐項證據:(1) ANILA UI(/home/aia/c1147259/ANILA/ANILA_UI/anila-ui/src)grep "banner|announcement|dismiss|motd|bulletin|notice|公告" 僅命中兩處註解:app.jsx:465「Drives the warning banner copy」指的是機密對話(classified)警示文案,屬對話層級的保密警告,非管理員公告;confirm.jsx:106 是 toast auto-dismiss 註解。無任何名為 Banner/Notice/Announce 的元件,grep "dismissed|dismissal" 零命中。(2) localStorage 用途盤點:全 src 只有 anila-folders(app.jsx:273,286)與 anila_dev(spanTree.jsx:257),完全沒有 dismissedBannerIds 類似機制。(3) CSP 後端(/home/aia/c1147259/ANILA/myCSPPlatform/backend/app)無 banner/announcement model 或 API:models/ 與 api/ 目錄列表中最接近的是 alerts.py + alert.py,但那是 require_admin 的「告警中心」(系統監控 alert,acknowledge/resolve 工作流,api/alerts.py:17,44),不是對一般使用者廣播的公告;conversations.py:107、memory.py:176、models/conversation.py:37 的 "banner" 註解同樣指機密升級警示。(4) CSP console 前端的 .secret-banner(ServiceClientsView.vue:85、DeveloperAgentsView.vue:266,415)是一次性 token 顯示框,DeveloperAgentsView.vue:126 的 .banner 是管理員待審核 agent 提示,皆非公告系統。(5) ANILALM(WSSidebar.tsx:215)只是 inline error banner。結論:open-webui 式「管理員設定公告 → 聊天頂部顯示 → 使用者關閉後記住」的整條鏈(後端 model/API + 前端顯示面 + 關閉記憶)在 ANILA 生態全缺,且為離線可用的純內網功能,對軍方內網佈告(如維護通知、保密提醒)有實際用途。最接近的既有物是機密對話警示橫幅,但它由 classification 狀態驅動、不可關閉、非管理員自訂內容,不構成 partial。

### [4分 / M] Per-chat export: JSON / TXT / PDF / copy
- **域**: organization | **狀態**: missing
- **說明**: open-webui 單一對話可下載 .json/.txt/.pdf（jsPDF+html2canvas 全 client 端，離線可用）或複製全文，受 chat.export 權限旗標管控。ANILA 無任何對話匯出（grep 全 src 確認）。
- **評估**: 軍中使用者把問答帶進公文/報告是高頻場景，目前只能逐則複製。TXT/Markdown 匯出是純前端 S 級工作；PDF 因 html2canvas 走瀏覽器渲染所以 CJK 字型沒問題但 bundle 變重。關鍵約束：必須比照現有 copy-disable 邏輯，classified 對話一律封鎖匯出，並建議寫 CSP audit log——這是引入時的硬性需求，不是選配。
- **驗證證據**: 證實缺漏。ANILA UI 全 src 無任何對話層級匯出機制：grep 無 jsPDF / html2canvas / new Blob / createObjectURL / 「匯出」字樣（唯一 .pdf 命中是 chat.jsx:1082 上傳 accept 屬性）。對話側欄選單僅有「重新命名」與「刪除對話」（chat.jsx:1500-1526），另一下拉是標籤/資料夾編輯器（chat.jsx:1486-1499）；runtime/conversations.js 只有 CRUD/分享/移交 API，無 export endpoint。相鄰但不等價的功能：單則助理訊息複製按鈕（chat.jsx:426-441、542-554，受 canCopy = !classified 管控，機密對話顯示「機密對話禁止複製」鎖）、程式碼區塊複製（markdown.jsx:99-100）、分享連結複製（collab.jsx:51）——皆為訊息層級，對應 open-webui 的 per-message copy 而非 per-chat export，無「複製全文」。ANILALM src/api/studio.ts:282-292 的「匯出 PDF/DOCX/Excel/CSV」是 Studio artifact job（報告/心智圖/資料表生成）的步驟標籤，非對話匯出；其 conversations.ts 亦僅 CRUD。CSP console 無相關功能。註：既有的 classified 複製管控模式可直接沿用為匯出權限旗標（對應 open-webui 的 chat.export），且 jsPDF 純 client 端方案符合離線內網限制，屬可補的真實 chat-UX 缺口。

### [4分 / M] Server-synced user settings (cross-device)
- **域**: personalization | **狀態**: missing
- **說明**: Open WebUI persists all UI settings server-side per user (/users/user/settings/update) so preferences follow the user. ANILA: folders live only in localStorage 'anila-folders' (verified app.jsx:273/286), tags/stars are client-state, and TweaksPanel settings aren't persisted anywhere.
- **評估**: The most important personalization gap for this deployment. PKI-card login on shared military workstations means (a) a user's folders/tags/stars/tweaks vanish on any other terminal, and (b) worse, localStorage is per browser profile, so on a shared terminal user B can see user A's folder names and conversation groupings — a small but real information-leak on a classified network. A per-user settings blob endpoint on the CSP control plane + migrating folders/tags/star/tweaks to it fixes persistence, sync, and the leak in one move.
- **驗證證據**: Confirmed absent across all three apps. ANILA UI: folders persist only to localStorage 'anila-folders' (app.jsx:270-290; data.jsx:3-4 comment says "persisted in localStorage"). Stars/tags/folder-assignment are pure React state and are RESET on reload — mapServerConversation (app.jsx:452-469) hardcodes folder:"all", tags:[], starred:false when loading conversations from the server, and runtime/conversations.js only PUTs {title} (updateConversationTitle, lines 43-48), never tags/star/folder. TweaksPanel settings (theme/accent/density/fonts) live in React state seeded from window.ANILA_TWEAKS (app.jsx:2385-2411) — no localStorage, no server call; tweaks.jsx has zero fetch/persist logic. The runtime API layer (runtime/api.js, runtime/conversations.js) has no settings endpoint; runtime/memory.js /api/memory/* is LLM long-term memory facts, not UI settings. CSP backend (myCSPPlatform/backend/app): no user-settings/preferences endpoint — api/users.py only has admin profile/role/allowed-models routes; models/conversation.py has no starred/tags/folder columns; models/user_memory.py is chat-injected memory, not preferences. ANILALM: grep for settings/preference matched only src/components/Icon.tsx (an icon). Gap is actually understated: tags/stars/folder-assignment don't even survive a same-device reload.
